### The physical scene that governs every decision

A guest is standing outside a 76 unit student housing block on Trongårdsvej in Kongens
Lyngby, at night, in October, on mobile data, slightly drunk, working out which of several
doors to walk through. Legibility under those conditions outranks every aesthetic
consideration. Where this spec breaks a design-taste guideline, it is because of that
sentence, and the break is stated rather than smuggled.

### Category-reflex check (anti-slop, run at both altitudes)

- **First-order reflex** for "location section with a map": a card with a pin icon, a
  "Find us" heading, a rounded map image, a "Get Directions" pill, and a three-up row of
  contact cards. **Refused.**
- **Second-order reflex** ("a location section that is not a SaaS contact block"): the
  editorial travel-guide look. Big serif "Getting here", a muted photograph, numbered
  arrival steps with airy whitespace. **Refused.**
- **What ships instead:** both sections are rendered as **course logistics documentation**,
  in the same institutional grammar as the CourseBase fact table already on the page. The
  address is a labelled data field in mono, exactly like `#fact-schedule` is. The map is an
  annexed plan drawing inside a hairline frame, not a rounded hero image. The notes are a
  definition list, not a card grid. **Zero icons anywhere in this phase.** No pin, no
  chevron, no play triangle beyond the browser's own native video controls.
- Why that clears both altitudes: it reads as page four of a course description PDF, which
  is neither of the two reflexes, and it is also the most legible possible answer outdoors,
  because institutional documents are already optimised for being read in a hurry under bad
  conditions by people who do not want to be reading them.

### Discretion call: the notes block lives in the ACCESS section

CONTEXT.md left this open. Decision: **access section, positioned between the written
directions and the video.**

1. Five of the seven seeded notes (entrance, floor, buzzer, what to bring, when to arrive)
   answer "how do I get in and what do I do on arrival", which is the access section's
   question. Parking and transit lean location, but a guest reading those is already in
   travelling mode and reaches access in one tap from the top nav.
2. **The location section must stay short.** Its job is four things read in two seconds:
   address, copy, directions, map. Bolting a seven-row list onto it dilutes exactly the
   section the core value depends on.
3. The access section is where the hero's "Which door" button lands. It is the
   arrival-moment section, and arrival-moment questions belong in it.
4. Placing notes above the player extends D-12's principle: text before video, because text
   is faster on bad signal.

### Discretion call: the back-to-map affordance is an INLINE LINK, not a button

1. It is a within-page jump, not an action. The page already has `.inline-link` doing
   exactly this in the fact table ("Register here").
2. A third large button in a section that already carries a video would compete with the two
   directions buttons, which are the real actions on the page.
3. Anti-slop: no duplicate CTA intent. A second prominent map affordance would duplicate the
   location section's own buttons.

It gets a `min-height: 44px` inline-flex box on coarse pointers so it is still tappable.

## Touch Target Geometry

44px is the floor. It is not the target. These get tapped one-handed, outdoors, in the cold,
possibly through a glove.

| Element | Fine pointer | Coarse pointer | Reason |
|---|---|---|---|
| Google / Apple directions buttons | 52px min-height | **56px min-height** | The primary outdoor actions. Apple's 44pt floor assumes an indoor two-handed tap. 56 also makes the pair read as the section's primary actions, which they are. |
| Copy address button | 48px (inherited `.btn`) | **52px min-height** | Secondary to the directions buttons, but still a cold-thumb target. |
| Back to map inline link | text baseline | **44px inline-flex box** | Secondary affordance. 44 is the correct floor here. |
| Video element | native | native | Browser owns the controls. Do not restyle them. |
| Map iframe | native | native | Google owns the interior. |

**Phone layout (`max-width: 480px`):** the three buttons in `.dirs` stack full-bleed at
`width: 100%`, mirroring the existing `.hero__actions` rule, with `gap: var(--s-3)`.
Order when stacked: **Google, Apple, Copy.** The two handoffs sit under the thumb; copy is
the least urgent of the three and takes the bottom slot. On wide screens the row is
`flex-wrap: wrap` in the same order, left-aligned.

Horizontal padding stays `0 var(--s-5)` (24px) from `.btn`, so the tappable area extends well
past the label glyphs.

## Interaction States

Every interactive element in this phase, across all eight states. Where a state is not
reachable, that is stated with the reason rather than a style being invented for it.

### 1. Copy address button (`.copybtn`, built on `.btn.btn--ghost`)

Four visible states are specified by the phase brief: idle, pressed, copied, failed.

| State | Treatment |
|---|---|
| **Default (idle)** | `.btn--ghost`. Label `t('loc.copy')`. Border `--rule-lit`, label `--ink`. |
| **Hover** | Inherited ghost hover: border and label go `--accent-lit`. Gated behind `@media (hover: hover) and (pointer: fine)`. |
| **Focus** | Global `:focus-visible`, unchanged: 2px `--accent-lit`, offset 3px, radius 2px. No bespoke ring. |
| **Active (pressed)** | `transform: scale(0.97)`, 140ms `--ease-out`. Inherited from `.btn:active`. |
| **Success (copied)** | Label swaps to `t('loc.copied')`. Border and label go `--accent-lit`. Reverts to idle after **2000ms**. `toast(t('loc.copied.toast'))` fires simultaneously. |
| **Error (failed)** | Both clipboard paths threw. The address text is programmatically selected via `Range` + `Selection`. Label swaps to `t('loc.copy.failed')`, label color `--accent-lit`. Reverts after **4000ms**. `toast(t('loc.copy.failed.toast'))` fires. |
| **Disabled** | **Not reachable by construction.** The button is absent from the DOM when `venue.address` is null, because the whole address block is replaced by `.pending`. No disabled style is defined, deliberately. |
| **Loading** | **Not applicable.** `navigator.clipboard.writeText` resolves in single-digit milliseconds. A loading state would be a flash, which is worse than none. |

**Failure treatment reasoning:** no red border box, no error icon. That reads as form
validation, which is the wrong register for "your browser refused an API call". The recovery
is the design: the text is already selected, so the guest's next action is a single long-press
menu away. Copy states the fact and points at the recovery.

**Asymmetric revert timing is deliberate:** success reverts at 2000ms, failure at 4000ms.
The failure string is longer and the guest is reading it while doing something else.

**How `toast()` participates.** Two feedback channels for one action is normally
over-signalling. It is correct here because on a phone the button is under the guest's thumb
at the moment its label changes, so they may never see it. The toast is bottom-center and
they will. Division of labour:

- **Button label** carries the short state word (`Copied`). Seen by desktop and keyboard users.
- **Toast** carries the full sentence. Seen by phone users. It is the announcer for assistive
  tech, because `#toast` already has `role="status" aria-live="polite"`.

The button itself gets **no** `aria-live`. Putting a live region on a control re-announces its
own label on every change, which is noise. The toast is the single announcement channel.

### 2. Directions handoffs (`a.btn--primary` Google, `a.btn--ghost` Apple)

| State | Treatment |
|---|---|
| **Default** | Google is `.btn--primary` (accent fill). Apple is `.btn--ghost`. |
| **Hover** | Inherited, gated behind `(hover: hover) and (pointer: fine)`. Google to `#B00000`, Apple to `--accent-lit` border and label. |
| **Focus** | Global `:focus-visible`, unchanged. |
| **Active** | `transform: scale(0.97)`, 140ms. Inherited. |
| **Disabled** | **Not reachable.** Absent from the DOM when `venue.address` is null. |
| **Loading** | **None, deliberately.** This is a navigation handoff. The browser and OS own the transition. A spinner would be a lie about who is working. |
| **Error** | **None, and no attempt at one.** There is no reliable signal for "did the native app open". Every heuristic (blur timing, visibility change, timeout) produces false negatives on slow devices and would show an error message to a guest whose map app opened perfectly. If the guest has no map app the OS falls back to the web version, which is a correct outcome. Documented as a refusal so nobody adds it later. |
| **Success** | **None.** Leaving the page is the success signal. |

Both carry `target="_blank" rel="noopener"`.

**Why Google is the accent button:** it works on every platform and is the universal answer.
Apple is the platform-specific convenience. This also keeps exactly one filled accent button
per section region, matching the accent discipline in the hero and the nudge bar.

### 3. Apple platform detection heuristic (discretion call, resolves D-06)

Evaluated in order. Any positive signal shows the Apple button.

1. `navigator.userAgentData?.platform` matched against `/mac|ios|iphone|ipad/i`.
2. `navigator.platform` matched against `/^(iPhone|iPad|iPod|Mac)/`. This also covers
   iPadOS 13+, which reports `MacIntel`, and a Mac desktop, where `maps.apple.com` correctly
   opens the Maps app.
3. `navigator.userAgent` matched against `/iPhone|iPad|iPod|Macintosh/`.

Outcomes:

- Any signal positive: **show Apple.**
- All signals present and clearly non-Apple (Android, Windows, Linux): **hide Apple.**
- All signals absent or unparseable: **show both** (D-06's inconclusive rule).

Explicitly forbidden: inferring the platform from `screen.width`, from touch support, or by
attempting to open the URL and measuring what happens. A privacy browser that spoofs its UA
falls into the "clearly non-Apple" branch and loses the Apple button. That is acceptable: the
Google button still works everywhere.

### 4. Map slot (`.map-slot`), three states

The iframe is never in the static markup (D-08). It is created in JS and mounted on
`IntersectionObserver` with `rootMargin: '400px 0px'`, so it is ready before the guest reaches
it and stays out of the critical path on mobile data.

| State | `data-state` | Treatment |
|---|---|---|
| **Mounting (default)** | `mounting` | The waiting layer is visible. Fixed ratio box, `--surface` fill, 1px `--rule` frame, radius `--r-sm`. See the waiting-state design below. |
| **Ready** | `ready` | `load` fired on the iframe. The waiting layer crossfades out over **220ms opacity only**, then `display: none`. The iframe was already at `opacity: 0` beneath it and fades in on the same 220ms. |
| **Blocked** | `blocked` | The `load` event has not fired after **8000ms**, or an extension or network blocked the Google embed. The waiting line swaps to `t('loc.map.blocked')` and the loader bar stops. |

**The blocked state does not tear the iframe down.** It is a message swap only. If `load`
fires at second 12 on a genuinely terrible connection, the slot still transitions to `ready`.
A timeout that destroys a working element is worse than the wait it was meant to fix.

Iframe attributes, all mandatory: `loading="lazy"`, `referrerpolicy="no-referrer-when-downgrade"`,
`title="{t('loc.maptitle')}"`, `src="https://www.google.com/maps?q={encoded}&output=embed"`.

**Do not add `sandbox`.** A sandboxed Google Maps embed cannot load tiles or run its own
scripts, so it renders blank. **Do not grant `allow="geolocation"`.** Nothing in this phase
needs the guest's position, and requesting it would put a permission prompt between a cold
guest and an address.

Focus: `.map-slot iframe:focus-visible { outline-offset: -3px; }` so the ring draws inside the
frame rather than colliding with the slot border. Precedent exists: `.facts__row--egg` already
uses `outline-offset: -2px` for the same reason.

Aspect ratio: `16/10` at or above 560px, `4/3` below it. A map on a narrow screen needs
vertical room to show two intersecting streets, which is the whole reason a guest looks at it.

### 5. The map waiting state (highlighted design item)

It is on screen for a real fraction of a second on bad signal, and a grey rectangle is a
wasted opportunity on a page whose entire personality is institutional deadpan.

**Composition,** inside the fixed-ratio box so nothing reflows when the iframe arrives:

1. **A 2px indeterminate loader bar** pinned to the top edge of the slot, `--accent-lit`,
   drawn as a pseudo-element at 25% width, translated horizontally from `translateX(-100%)` to
   `translateX(400%)` on a 1100ms `linear` infinite loop. Parent has `overflow: hidden`.
   Transform only, GPU, no layout work. Linear is the correct easing for constant indeterminate
   motion. It reads as the progress rule at the top of a document viewer, not as a spinner.
2. **One centered line of copy,** IBM Plex Mono 13px, `--ink-dim`, `text-wrap: balance`,
   `max-width: 34ch`, centered both axes.

**The copy is the actual design work here,** not the texture. The guest's real question during
those seconds is "do I have to wait for this". The answer is no, because the address and both
directions buttons are already above it and already work. So the line says exactly that:

> EN: `Map loading. The address above works without it.`

That turns dead time into reassurance, in the institutional register, and it is the difference
between a placeholder and a decision. The blocked state's line does the same job for the
failure case, pointing back at the affordances that still work.

**No graph-paper texture, no repeating-linear-gradient, no skeleton shimmer, no map-pin
silhouette.** All four were considered and rejected: the first two are catalogued anti-slop
decoration, the third fakes content shape for content whose shape we cannot predict, and the
fourth is the exact first-order category reflex this spec refused at the top.

Reduced motion: the loader bar gets `animation: none`, sits static at full width, `opacity: 0.35`.
The copy line already carries the meaning, so nothing is lost.

### 6. Video player (`.video-slot > video`)

Attributes, locked by D-13 and ACC-01: `playsinline muted controls preload="metadata"`, plus
`poster` **only when `door.posterSrc` is configured.** An empty `poster=""` attribute breaks
rendering in some browsers, so the attribute is omitted entirely rather than set to a falsy
value.

| State | Treatment |
|---|---|
| **Default, poster configured** | Poster frame fills the slot. |
| **Default, no poster** | The slot's own `--surface` background shows through. The `<video>` element itself carries `background: var(--surface)` and `object-fit: contain`, so letterboxing bars and any unpainted frame are institutional grey, never black. This is the concrete answer to ACC-03 and D-14 when no poster exists. |
| **Hover / Active** | Native. **Do not restyle native video controls.** A hand-rolled player is pure failure surface on iOS Safari, and `controls` is required by ACC-01. |
| **Focus** | The `<video>` is focusable. Global `:focus-visible` ring applies, drawn outside the slot. |
| **Loading** | Native. `preload="metadata"` may leave the poster up for a while on bad signal, which is correct behaviour and needs no addition. |
| **Error** | The `error` event fires (wrong path, missing file, unsupported codec). JS replaces the slot contents with the `.pending` panel described below. **No developer-facing message ever reaches the guest.** |
| **Disabled** | Not reachable. Absent when `door.videoSrc` is null. |
| **Success** | Playback. Nothing added. |

**Reusing the pending copy for a 404 is deliberate.** To the guest, "the file is missing" and
"the file was never made" are the same event and the same correct message. The owner catches
the difference from the README placeholder checklist, not from the guest-facing UI.

`controlsList="nodownload"` is **not** set: Chrome-only, and preventing download serves nobody
here.

### 7. The unconfigured video state (highlighted design item)

This ships first. It may be what most guests see for weeks. It must read as documentation
pending, in the parody's voice, not as a broken player.

**It is a `.pending` block placed inside `.video-slot` at the player's configured aspect
ratio.** That single decision satisfies three things at once:

- D-18: reuse the established placeholder language, do not invent a second one.
- D-14: a styled panel at the player's exact ratio. Never a black rectangle, never a collapsed box.
- Zero layout shift on the day the owner sets `door.videoSrc`. The section's height does not move.

Content, both strings already live in all three languages from phase 1:

- `.pending__t` = `t('access.pending.title')` = "Access documentation pending"
- `.pending__b` = `t('access.pending.body')` = "A short clip showing the correct door is being
  produced. Until then, ask the person who invited you, or follow the noise."

That title is, word for word, the requested "documentation pending in the parody's voice". It
was written in phase 1, it is already deployed, and re-translating it would be churn.

Geometry: the `.pending` inside the slot takes `height: 100%; max-width: none;` and its content
sits **top-aligned** with the panel's own `var(--s-5)` padding. It **fills** the slot rather
than floating centered inside it, because a centered card inside a bordered box is a nested
card, which is always wrong. One box, one border, one panel.

### 8. Video aspect ratio, and the portrait trap

**Risk this spec is heading off:** the owner will almost certainly film the door on a phone,
held upright. A 9:16 clip dropped into a hardcoded 16:9 slot letterboxes into black pillars,
which is precisely the black rectangle D-14 forbids.

Contract:

- `config.js` gains `door.aspect`, default `'16/9'`, documented for a non-programmer as
  *"if you filmed it upright on your phone, change this to 9/16"*.
- JS sets `--video-aspect` inline on `.video-slot` from that value, and sets
  `data-orient="portrait"` when the numerator is smaller than the denominator.
- CSS:
  - `.video-slot { width: 100%; max-width: 760px; margin-inline: auto; aspect-ratio: var(--video-aspect, 16/9); }`
  - `.video-slot[data-orient="portrait"] { max-width: 360px; }`

Deterministic, no viewport-unit arithmetic, no fights between `aspect-ratio` and `max-height`,
and it holds for both the player and the pending panel because they share the slot.

### 9. Written directions (`.steps` / `.dir-prose`)

`door.directions` accepts **either a string or an array of strings.**

- **Array:** renders as an ordered list reusing the `.objectives` counter pattern already in
  `styles.css`: `counter-reset` / `counter-increment`, `decimal-leading-zero`, numeral in
  IBM Plex Mono 13px `--accent-lit`, hairline `--rule` between rows, 17px body text.
- **String:** renders as one `<p class="dir-prose">` at 17px / 1.5 / `max-width: 60ch`.
- **Null:** `.pending` block with the NEW `access.dir.pending.*` copy.

**Why both shapes:** a numbered walking sequence read at night is dramatically faster to follow
than a prose sentence, and it costs about six lines of JS. This is the single highest-value
legibility decision in the phase. Prose stays supported because the owner may write one clean
sentence and should not be forced into an array to do it.

Anti-slop note: the banned pattern is *generic step labels* ("Step 1", "Stage 2"). This renders
the actual instruction with a leading numeral, which is the `.objectives` pattern already
shipped on this page. No label word is added.

Zero-one-many: an array of one renders as a single row numbered `01`. Slightly formal, entirely
consistent with the institutional register, accepted.

### 10. Practical notes (`dl.facts.facts--notes`)

Visual form: **echo the existing `.facts` definition list.** The brief says DTU pages are
information dense and that density is part of the parody, so the page's own institutional list
component is reused rather than a card grid being invented.

`.facts--notes` differs from `.facts` in exactly one property: the label column narrows from
`minmax(180px, 260px)` to `minmax(140px, 200px)`, because note labels are short words
("Entrance", "Floor") rather than phrases ("Language of instruction"). Everything else is
inherited: hairlines, `dt`/`dd` colors and sizes, the single-column collapse at 640px.

Config shape, values only, keys fixed:

```js
venue.notes = {
  entrance: null, floor: null, buzzer: null,
  parking: null, transit: null, bring: null, arrive: null,
}
```

Render order is fixed and deterministic: **entrance, floor, buzzer, parking, transit, bring,
arrive.** Door information first, because the section is optimised for a guest already standing
outside. Pre-departure information (what to bring, when to arrive) sits last.

- Any entry null: that row is absent. No "n/a" filler, no empty row (D-16).
- All entries null: the sub-heading and the entire `dl` are absent. Not an empty shell.

**Labels live in `copy.js`** (keys `notes.entrance` through `notes.arrive`) so a Danish guest
does not hit an English label. **Values live in `config.js` and are shown exactly as written,
in every language.** That is an accepted, documented tradeoff: an address fragment like
"3. sal" or "ring 46" should not be translated anyway, and per-language config objects are a
structure a non-programmer will get wrong. The config comment must say so plainly:
*"These are shown exactly as you write them, in every language. Keep them short and factual."*

### 11. Jump path to the door (D-20)

Already served by the hero "Which door" button and the `.topnav__key` entry. Smooth scrolling
and its reduced-motion fallback are **already in `styles.css`**:

```css
html { scroll-behavior: smooth; scroll-padding-top: calc(var(--topbar-h) + var(--s-4)); }
@media (prefers-reduced-motion: reduce) { html { scroll-behavior: auto; } }
```

**No JS scroll handler is added.** No new pinned element is added: NDG-02 reserves the bottom
bar for the nudge, and a second fixed element would fight it on a phone.

## Motion Contract

MOTION_INTENSITY **3** for these two sections (D-21). Exactly five motion decisions exist, and
two of them are refusals. Every one is `transform` or `opacity` only. Every one ships its
`prefers-reduced-motion` fallback **in this phase** (D-22), not retrofitted in phase 5.

| # | Motion | Duration / easing | Purpose (one sentence) | Reduced-motion fallback |
|---|---|---|---|---|
| 1 | Button `:active` scale to 0.97 | 140ms `--ease-out` | Confirms the interface heard a cold thumb. | Inherited global rule collapses transition to 0.01ms, so it becomes an instant state change. Feedback survives. |
| 2 | Map loader bar `translateX` | 1100ms `linear`, infinite | Indicates an indeterminate wait with no fake progress claim. Linear is correct for constant motion. | `animation: none`. Bar static at full width, `opacity: 0.35`. The copy line carries the meaning. |
| 3 | Map ready crossfade | 220ms `--ease-out`, **opacity only** | Prevents a jarring swap when the iframe lands. | Global rule collapses to 0.01ms: an instant swap. Correct and honest. |
| 4 | Copy button label swap | **No animation, deliberately** | The label is six characters and the guest's thumb is on it. A crossfade on a word someone is about to read is worse than an instant change. | n/a |
| 5 | Scroll to `#access` / `#location` | Native `scroll-behavior: smooth` | Spatial continuity on an in-page jump. | Already handled: `scroll-behavior: auto`. |

**Explicitly refused in this phase, so phase 5 knows these were considered and rejected rather
than forgotten:** section entrance animation, map mount slide-in, video reveal, and stagger on
the notes list. All four are gated by DSG-07 (the practical information is never behind an
animation) and by MOTION_INTENSITY 3. A stagger on the notes list would specifically animate
the exact rows a guest is squinting at, which is the worst possible place to put one.

No `transition: all` anywhere. No keyframes on anything a guest can retrigger rapidly. No
`ease-in` on any UI element.
