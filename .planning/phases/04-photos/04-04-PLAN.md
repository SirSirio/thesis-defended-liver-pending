    Add `classifyStorage(out)` and `classifyPhotoInsert(res)` as two separate functions, each carrying
    a comment naming which service it serves and why the two cannot be merged. Storage answers an
    outer HTTP 400 for every failure with the real status as a string inside the body, and its code
    field carries a name rather than a Postgres code; PostgREST answers the real status with a
    Postgres code. A classifier shared between them silently mis-branches, and the risk is not the
    first write but a later refactor that unifies them.

    `classifyStorage` maps a synthesised network outcome to `photos.err.network` and every other
    non-success to `photos.err.server`. It never branches on an outer status literal for a condition
    whose real status lives in the body. `classifyPhotoInsert` returns one of three names: recorded,
    at the limit, or failed, the limit branch keyed on the Postgres raise-exception code and never on
    the message string, which is English, unstable and embeds constraint names.

    Wire both into the driver. A file whose upload fails becomes a `failed` row carrying the key its
    classifier returned, and the driver continues to the next file rather than aborting the batch.
    A file whose row insert fails for any reason other than the limit becomes a `failed` row carrying
    `photos.err.server`, and its uploaded object is left where it is: nothing in the browser can
    remove it, it appears in no view, no page and no URL anyone holds, and it is the cheaper of the
    two asymmetric failures D-19 chose between. Carry that as a written accepted consequence in a
    comment beside the branch, not as a defect.

    Add `settleBatch()`, called once when no record is left waiting. It counts the recorded, refused
    and failed records and writes the terminal control state: `success` when everything landed,
    `refused` when everything was refused, `failed` when nothing landed, and `partial` when the batch
    was mixed. It then composes the two live regions. The status line, which is polite, carries
    `photos.status.done.one` or `photos.status.done.many` on success and `photos.status.partial` with
    the two counts substituted on a mixed batch, and stays hidden when nothing landed. The alert
    line, which is assertive, carries the failure and refusal sentences and stays hidden on a clean
    success. A failure is worth interrupting for and a counted progress sentence is not.

    guest picks again, which is the same rule phase 3 set for its form and is what makes task 2's
    retry possible at all.
