# Phase 4 — UI Design Contract

> Visual and interaction contract for the photo upload control, the five-photo limit and its
> refusal, the shared album, and the closed, unconfigured and not-registered states.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This phase builds the site's first file input, its first determinate progress indicator, and
> its first image grid.** Everything under `## The Upload Component System` and `## The Album
> Component System` is NEW. Everything under Design System, Spacing, Typography and Color is read
> out of the deployed `styles.css` unless a row is marked **NEW**.
>
> **This phase adds zero design tokens, zero type sizes, zero font weights, zero font families and
> zero colour values.** Every value below already ships. That is a deliberate constraint. An upload
> control with nine states and a photo grid are the two places where an ad hoc design system gets
> invented, and this contract exists to stop that happening in the loudest section of the page.
>
> **Zero em dashes and zero en dashes appear in this document**, matching the ledger house style
> and DSG-06. The single exception is the H1 above, whose form is fixed by the UI-SPEC template and
> matches the phase 2 and phase 3 contracts.

### The physical scene that governs every decision

A guest is standing in a room at a party, on a mid-range phone, on congested mobile data or
contended wifi, holding the phone in one hand, using one thumb, with a photo they took ninety
seconds ago. The roadmap's done-when sentence is **"a phone can upload five photos and see them in
the album, and the sixth is refused with a joke rather than an error."** That sentence outranks
every aesthetic decision in this document. Where this spec breaks a design-taste guideline, it is
because of that sentence, and the break is stated rather than smuggled.

The brief's own hard constraint still outranks everything: countdown, address and door video are
readable in under three seconds by someone standing outside a building in the dark. Nothing in
`#photos` may compete with those three, which is one more reason the spectacle waits for phase 5.

### Category-reflex check (anti-slop, run at both altitudes)

- **First-order reflex** for "photo upload on a party site": a dashed-border drop zone with a cloud
  arrow icon, "Drag and drop your files here, or click to browse", a blue or gradient progress bar,
  a grid of rounded cards with a hover lift and a soft shadow, a green checkmark and confetti on
  success, a lightbox with a blurred backdrop. **Every item refused.**
- **Second-order reflex** ("an upload that is not a party upload"): the premium consumer gallery.
  Masonry with mixed aspect ratios, hover scale with a `bg-gradient-to-t from-black/60` caption
  scrim, a floating pill FAB, a full screen viewer with keyboard navigation, skeleton shimmer while
  the images load. **Refused.** This is exactly what the two routed skills reach for. See
  `## Routed-Skill Conflicts`.
- **What ships instead: the hand-in, and the contact sheet.**
  - The **upload control is a coursework submission**. The remaining count is a labelled data field
    in the fact-table grammar the guest already met at the top of the page and again in their
    registration receipt. The control is a real button carrying a verb. The batch in flight is a
    **submission transcript**: numbered rows, file name, state word, and a table rule under each row
    that doubles as that file's progress bar. The register joke that D-07 deliberately kept out of
    the album lives here instead, where it is genuinely a log of a transaction in progress and where
    it disappears when the transaction ends.
  - The **album is a departmental contact sheet**. A regular square grid, each frame with a hairline
    and a caption band below it naming the submitter in institutional micro-type. The register
    (count, empty, retrieving) sits in the chrome above the grid, which is what D-07 asked for in
    those words. The photographs get to be photographs.
  - **Zero icons anywhere in this phase**, the same refusal phases 2 and 3 made. No cloud, no
    checkmark, no chevron, no spinner glyph, no hand-drawn SVG.
- **Why that clears both altitudes:** it reads as the assignment hand-in page of a course
  description, which is neither reflex, and it is also the fastest possible answer for a guest with
  a photo and one thumb, because it introduces no component grammar they have to learn.

### The drop zone is refused, explicitly

There is **no drag-and-drop target in this phase**, and no `dragover` handler.

1. The done-when sentence is about a phone. Drag and drop is a gesture that does not exist on the
   device this ships to.
2. A drop zone that only functions on desktop is the largest single piece of UI in the control,
   dead weight for the overwhelming majority of traffic, and it would be the biggest box on the
   page.
3. It is the single most recognisable AI-slop artifact in this problem space, and the project's
   whole aesthetic argument is that it does not look like that.

A desktop guest taps the same button and gets the operating system's file dialog, which already
supports every selection method the operating system has.

## Spacing Scale

Inherited from `:root`, on a 4px base. **This phase adds no token.**

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| `--s-1` | 4px | File name to its refusal reason inside a queue row |
| `--s-2` | 8px | Album grid gap below 900px; album caption band padding; queue index to file name |
| `--s-3` | 12px | Remaining-count field to the permanence line; status line to the queue; queue row vertical padding; album grid gap at 900px and up |
| `--s-4` | 16px | Album head to the grid; between stacked action buttons |
| `--s-5` | 24px | Permanence line to the submit button; submit button to the status line |
| `--s-6` | 32px | Queue to the album head; panel body to its call to action |
| `--s-7` | 48px | Upload block to the album block. Two separate answers to two separate questions, the same rhythm phase 3 used between the form and social proof. |
| `--s-8` / `--s-9` / `--s-10` | 64 / 96 / 128px | Section block padding, inherited via `.section` |

**Exceptions:** none. Every spacing value in new CSS is a token from the scale above. Exactly four
literal pixel values are permitted, and this list is closed:

1. Element minimum sizes (48px, 52px, 56px), documented under Touch Target Geometry.
2. `2px` for `.queue__bar` height, which matches the existing `.sweep` and is a component height
   rather than a spacing value.
3. `1px` for hairlines, matching every existing hairline in the file.
4. `aspect-ratio: 1 / 1` on `.album__frame`, which is a ratio and not a length.

### Spacing decisions specific to this phase

| Relationship | Value | Reason |
|---|---|---|
| Queue row vertical padding | `var(--s-3) 0 calc(var(--s-3) + 2px)` | 12px, plus the 2px the bar occupies at the bottom edge, so the optical rhythm is 12px on both sides of the text and the bar sits exactly where the row's separating rule would have been. |
| Album grid gap | `var(--s-2)` below 900px, `var(--s-3)` at 900px and up | 8px at phone widths keeps two columns as large as possible on a 320px screen, which is the whole point of a thumbnail. 12px at desktop stops a four across sheet reading as a single mosaic block. |
| Album caption band padding | `var(--s-2)` | 8px all round. Any less and a name touches the frame edge; any more and the band competes with the photograph for height. |
| Upload block to album block | `var(--s-7)` | 48px, matching phase 2's sub-block rhythm and phase 3's form to social proof gap. |
| Status line reserved height | `min-height: var(--s-5)` (24px) | The status line holds its box in every state, so the submit button and the album below it never move when a batch starts or ends. Same no-reflow guarantee phase 2 gave the map slot and phase 3 gave the field error box. |

**The album caption is mono, and that is the joke doing structural work.** A photo credit set in the
body face reads as a social feed byline. The same string in IBM Plex Mono at 13px, in a hairline
band under the frame, reads as a specimen label on a departmental contact sheet. One family change
carries the entire register of the album, at a cost of zero new tokens.

**The album caption is not uppercased.** Two reasons. It is a guest-supplied name, and
`text-transform: uppercase` mangles names such as `de Luca` and disagrees with how Danish and
Italian names are actually written. And an uppercase micro-label here would be a second eyebrow
against a page-wide budget of two, one of which the hero already spends.

**The remaining-count figure is mono with tabular figures**, for the same reason the countdown is:
the number changes as photographs land, and a proportional face would shift the value cell sideways
every time it does.

**Queue file names use `overflow-wrap: anywhere` and a two-line clamp is not used.** A long camera
name wraps rather than truncating with an ellipsis, because a truncated file name is unidentifiable
and the entire purpose of the name cell is to let a guest tell one refused file from another. The
index numeral is the guaranteed disambiguator when the operating system supplies identical names.

**Wrapping and overflow:** `.album__by`, `.queue__name` and `.queue__reason` all carry
`overflow-wrap: break-word`. `.album__by` additionally carries `overflow: hidden` on a single line
with `text-overflow: ellipsis`, because a 40 character first name would otherwise grow one tile
taller than its neighbours and break the grid's row rhythm. The full name is in the anchor's
`aria-label`, so nothing is lost to assistive technology.

### The destructive-colour honesty note

**There is no destructive action in this phase and the template row is not applicable.** Nothing can
be deleted from the browser: no delete policy exists on `public.photos` or on `storage.objects`, by
design, and V2-01 is the acknowledgement that this is known and deferred.

The consequence is that the only irreversible act in the phase is the upload itself, and the
disclosure has to happen **before** the guest commits rather than in a confirmation after. That is
what `.uploader__note` is, and it is why it sits above the button rather than below it. It is the
pre-commitment substitute for a destructive confirmation, and it is recorded as such rather than
left as a stray sentence.

**A confirmation dialog before each upload is explicitly refused.** It would put a modal between a
guest and the one thing this section exists to do, at a party, for an act every guest already
understands. One honest sentence, read before the picker opens, is the correct weight.

fail SC 1.4.11 if it were the thing that identifies the tile as a control. It is not. The tile is
identified by the photograph it contains and by the caption naming its submitter, both of which are
high contrast content, and its accessible name is on the anchor. The hairline is contact-sheet
framing. Pointer users additionally get a `--ink-faint` border on hover at 3.88:1, and keyboard
users get the 4.90:1 focus ring. Recorded as a considered judgement, not an oversight.

- **`--ink-faint` for the queue index numeral.** 3.88:1 against `--bg`, below the 4.5:1 body floor.

- **`--ink-faint` for the completed progress fill.** 2.82:1 against the `--rule` track. Replaced by

- **A translucent black gradient scrim over the bottom of each photograph, with the name on top.**
  It is the reflex treatment, and it is a contrast gamble against arbitrary photograph pixels that
  cannot be computed in advance: a name over a bright sky fails and there is no way to know at build
  time. The opaque caption band below the frame is a fixed, verifiable 7.15:1 and costs one hairline.

### Discretion call: the upload control sits above the album

Three reasons, in order of weight.

1. During the party the section's job is to receive photographs. The guest arrives holding one.
2. The album grows without bound and has no pagination (D-11). Below the album, the control would be
   one screen down at twenty photographs and eight screens down at two hundred, on the night it
   matters most.
3. After a successful upload the album refetches with the guest's own photograph at the top (D-09,
   D-12), which lands it immediately below the control. The confirmation is therefore visible
   without a scroll, without a toast and without a programmatic jump.

### Discretion call: the remaining count is a labelled data field, not a chip and not a button label

Rendered as `dl.facts.facts--record` with exactly one row: label `photos.remaining.label`, value the
integer in `.mono` with tabular figures.

1. Every quantity on this site is a labelled data field: ECTS points, expected attendance, the
   course number. A chip would be the only chip on the page and would arrive with a radius, a fill
   and a padding scale that nothing else uses.
2. Folding it into the button label ("Submit photographs (3 left)") makes the label change length on
   every upload, which reflows a full width button under a thumb and puts the Danish label at
   genuine risk of wrapping to two lines, which is a pre-flight failure.
3. A labelled figure needs no verb and is read at a glance, which is the whole requirement PH-02
   states.

The value updates live as each photograph is recorded, 5 to 4 to 3. **It is not animated.** A count
up on the one number a guest actually wants to read was refused in phase 3 for the attendance figure
and is refused here for the same reason, plus the arithmetic one: a text change is neither
`transform` nor `opacity`.

### Discretion call: the permanence line sits above the button, not below it and not in the lede

Adopted from the RESEARCH.md recommendation for open question 3 ("beside the control, before the
upload"). Sharpened here: **above** the button.

It is information a guest needs in order to decide, so it has to be read before the picker opens.
Below the button it would be read after the decision, if at all. In the section lede it would be
read once, on a page the guest scrolled past three hours earlier.

### Discretion call: the album grid is square-cropped, at explicit breakpoints

```
.album { display: grid; gap: var(--s-2); grid-template-columns: repeat(2, 1fr); }
@media (min-width: 560px) { .album { grid-template-columns: repeat(3, 1fr); } }
@media (min-width: 900px) { .album { grid-template-columns: repeat(4, 1fr); gap: var(--s-3); } }
```

- **Explicit breakpoints rather than `repeat(auto-fill, minmax())`.** `auto-fill` at a 1080px wrap
  and a sensible phone minimum produces seven columns at desktop, which turns a contact sheet into a
  mosaic of unreadable stamps. Four across at 1080px gives roughly 258px tiles, which is a
  photograph. Two across at 320px gives roughly 132px tiles, which is a tappable thumbnail with room
  for a name under it.
- **Square crop via `object-fit: cover`, not aspect preserving.** A party album is a mix of portrait
  and landscape phone photographs. Aspect preserving inside a fixed box produces letterbox bars on
  every second tile; aspect preserving without a fixed box produces ragged rows and breaks the
  no-reflow guarantee D-11 inherits from phase 2. A centre crop survives a thumbnail whose job is to
  be tapped, and the uncropped frame is one tap away at the public URL (D-10).

### Discretion call: the caption is always visible, and it sits below the frame

- **Always visible, never hover or focus only.** Hover does not exist on the device this ships to,
  so a hover-only caption would be invisible to substantially all real users, and PH-04 requires the
  album to display uploads *with the uploader's name*. Hiding the name behind an interaction fails
  the requirement.
- **Below the frame in its own band, not overlaid.** See the rejected scrim in `## Color`. The band
  also gives the tile a fixed, computable height, which is what lets the grid rows stay level when
  one name is longer than another.

## The Opening Gate

D-03 and D-04 own the arithmetic. This section owns what a guest sees, and closes one gap that
neither CONTEXT.md nor RESEARCH.md addressed.

### Adopted from RESEARCH.md recommendation (open question 1): the closed panel does not tick

**No countdown in the closed panel.** The hero already owns the ticking, and one clock per page is
the rule. The panel states the opening moment as text (D-05), formatted with the per-language
locales on `Europe/Copenhagen` that `formatSchedule()` already uses.

### The gap this closes: the gate is re-evaluated without a reload

A guest sitting on the page at 12:59 when uploads open at 13:00 must not be stranded on a closed
panel until they think to reload. But adding a second timer would be a second clock, and adding a
visible countdown was just refused.

**Contract:** the boolean `photosOpen()` is re-evaluated on the countdown's **existing** tick and on
`visibilitychange`. Nothing is re-rendered unless the boolean **flips**, at which point
`renderPhotos()` runs once and the closed body is replaced by the upload body.

- Zero new timers. Zero new intervals. One clock on the page, still.
- The comparison is an integer compare against a precomputed epoch millisecond value, so the
  per-tick cost is nothing.
- Re-render happens on a transition only, so a guest reading the closed panel does not have it
  rebuilt under them once a second.
- The transition is a body swap, so it uses the same 220ms opacity-only treatment as every other
  body swap in this phase.

`isNaN` handling cuts the opposite way from the countdown, and this is load bearing: **an
unparseable or absent `opensAt` falls back to open**, never to closed. D-05 makes
`photos.opensAt: null` the owner's one line recovery from a phone with the wrong date, on the night,
with nobody at a laptop. A typo in that field must not lock the album shut. Write it as: closed only
when there is a valid timestamp in the future.

### The countdown must not invite guests to a closed portal

CD-04's "it is over, upload your photos" state and this gate describe the same moment from two
sides. With the D-03 default of party start minus three hours,
`opensAt < startsAt < endsAt` holds and the countdown's `over` state always lands inside the open
window. The `config.js` comment beside `opensAt` names that relationship, which is the cheapest
possible guard against an owner moving one value on the night.

## The Upload Component System

### Markup contract

```html
<div class="uploader" data-state="idle">

  <dl class="facts facts--record">
    <div class="facts__row">
      <dt>Submissions remaining</dt>
      <dd class="mono">5</dd>
    </div>
  </dl>

  <p class="uploader__note">Anything you submit stays in the album for everyone. It cannot be taken back from here.</p>

  <div class="uploader__acts">
    <button type="button" class="btn btn--primary" id="photos-pick">Submit photographs</button>
  </div>

  <input type="file" id="photos-input" accept="image/*" multiple hidden>

  <p class="uploader__status" role="status" hidden></p>
  <p class="uploader__alert"  role="alert"  hidden></p>

  <ol class="queue" hidden></ol>

</div>
```

Non-negotiable structural rules:

- **The visible control is a real `<button type="button">`, and the `<input type="file">` is a
  separate sibling carrying the `hidden` attribute.** The button calls `input.click()` from inside
  the click handler, which is a user gesture and is the standard supported pattern. Three reasons
  this shape rather than a `<label>` wrapping the input:
  1. A native file input's own button label is rendered in the **browser's** language, not the
     site's, which would break LNG-06 the first time a Danish guest with an English browser opened
     the section. This is the identical reasoning phase 3 used for `novalidate`.
  2. A `<label>` cannot be `disabled`. The control must be genuinely disabled while bytes are in
     flight, and faking that with `aria-disabled` plus `pointer-events: none` is a worse control
     than a real button.
  3. The button inherits `.btn`, its `:active` scale, its hover rule and the global focus ring for
     free, with no bespoke styling.
- **`hidden` on the input rather than `.sr-only`.** `.sr-only` leaves the input focusable and in the
  accessibility tree, which would need `tabindex="-1"` plus `aria-hidden="true"` on a form control,
  a combination that is both a lint failure and genuinely confusing to assistive technology. The
  `hidden` attribute removes it from both, and `[hidden] { display: none !important; }` already
  exists in the Base block from phase 3. **Device pass item:** the picker opens from a `hidden`
  input on real iOS Safari and real Android Chrome.
- **`accept="image/*"` exactly, and it is never extended.** Adding `image/heic`, `.heic` or `.heif`
  makes Safari 17 and later hand back an actual HEIC file where `image/*` alone receives an
  operating-system-converted JPEG, and Android Chrome then cannot decode it. The line carries a
  comment saying it is deliberate and naming the regression, because it looks like an omission.
- **`multiple` is set** (D-15). A guest with five photographs picks five once.
- **The status and alert nodes exist from first render, `hidden`, and are unhidden and filled.** Many
  screen readers will not announce a live region inserted at the same moment its content is written.
  This is the same rule phase 3's `.form-alert` established.
- **Two live regions, two urgencies.** `role="status"` is polite and carries progress and success.
  `role="alert"` is assertive and carries refusals and failures. A failed upload is worth
  interrupting for; "Sending 2 of 3" is not.
- **Every string in this phase is written by `renderPhotos()` through `t()` and `textContent`. This
  phase adds no `data-i18n` attribute anywhere.** That is a deliberate departure from phase 3's form
  and it removes an entire class of bug: the language sweep cannot overwrite a substituted value
  with a raw template, and it cannot leave half the control in one language while the render is
  skipped mid-upload.
- **Guest-supplied and database-supplied values are only ever written with `createElement` plus
  `textContent`, or set as properties.** Never `innerHTML`, never a template string, never
  `insertAdjacentHTML`. The album caption renders one guest's name into every other guest's browser,
  which is the same exposure phase 3's attendee list opened.

### The queue markup contract

```html
<li class="queue__row" data-state="uploading">
  <span class="queue__n">2</span>
  <span class="queue__name">IMG_4821.jpg</span>
  <span class="queue__state">Sending</span>
  <p class="queue__reason" hidden></p>
  <span class="queue__bar"><span class="queue__fill"></span></span>
</li>
```

- **The index numeral is not decoration.** iOS returns identical file names (commonly `image.jpg`)
  for several picks from some camera-roll paths, so five rows can legitimately read the same. The
  numeral is what makes the transcript, and D-15's refusal message, actually identify a file. When
  `file.name` is empty the name cell renders `photos.queue.unnamed`.
- **`.queue__bar` is the row's separating rule and its progress track at the same time.** It is 2px
  tall in every state, `background: var(--rule)`, pinned to the row's bottom edge, `overflow:
  hidden`. It never changes size, so nothing below it moves at any point in the batch. This is the
  one genuinely bespoke idea in the phase: the institutional table rule under each log entry is the
  thing that fills up while that file uploads.
- **`.queue__fill` animates with `transform: scaleX()` and `transform-origin: left center`. Never
  `width`.** `width` is a layout property and DESIGN-BRIEF.md permits `transform` and `opacity`
  only. This is not pedantry: a width transition on a bar that updates on every `progress` event
  triggers layout on every event, on a phone, while the same phone is decoding the next image.
- **Fill colour carries state, and the state word carries the meaning.** In flight the fill is
  `--accent-lit`. On `done` it holds at `scaleX(1)` in `--ink-dim`, which reads as a completed
  entry. On `refused` and on `failed` the fill stays at `scaleX(0)` and the track remains a plain
  hairline, which is honest: nothing was recorded, so no line was drawn. Colour is never the only
  signal, because `.queue__state` names every state in words (WCAG 1.4.1).
- **The reason node is `hidden` when there is none**, so a healthy row is two lines of mono and a
  rule, not three.

### The progress honesty contract (PH-05, research Pitfall 5)

`xhr.upload.onprogress` reports bytes handed to the socket, not bytes the server has accepted. On a
bad connection the bar completes and then nothing happens for several seconds, which is
indistinguishable from a hang, and that is exactly the "is this broken?" moment PH-05 was written
against, wearing a new costume.

**Contract:**

| Reported | Visible fill | Row state word |
|---|---|---|
| 0 to 0.92 | `scaleX(reported)` | `photos.queue.uploading` ("Sending") |
| above 0.92, response not yet in | held at `scaleX(0.92)` | swaps to `photos.queue.recording` ("Recording") |
| `onload`, 2xx | `scaleX(1)`, fill goes `--ink-dim` | `photos.queue.done` ("On record") |
| `lengthComputable` false | `scaleX(0.92)` held from the start | `photos.queue.recording` from the start |

The dead wait becomes a **named step** rather than a stalled bar. The bar never claims 100% until
the server has answered, and the site never draws a bar it cannot honestly fill: where the browser
refuses to report progress at all, the state word does the work and the bar does not pretend.

**There is no aggregate progress bar.** The aggregate is a counted sentence ("Sending 2 of 3") in
`.uploader__status`, and the per-file bar is the only bar. Two bars for one operation are two
progress claims about the same thing, and the second one is always the one that lies.

### The batch model

- The queue is rendered from a **JavaScript array of file records**, not read back out of the DOM.
  Each record holds the `File`, the index, the state, and the copy key of its reason. This is what
  makes a language switch safe in every settled state, and it is what keeps the `File` objects alive
  for a retry.
- **Picking a new batch clears the queue and discards any un-retried failed files.** PH-05 is
  satisfied because the guest was told, by name, what did not land and was offered a retry before
  they chose to move on. A queue that accumulates across batches grows without bound during exactly
  the hours when the phone is busiest.
- **`failed` and `refused` never clear the selection.** The records survive until the guest picks
  again, which is the same rule phase 3 set for its form.

### Language switch during a batch (research Pitfall 7)

`renderPhotos()` joins the `applyLanguage()` chain, so a guest tapping DA mid-upload would otherwise
get the control rebuilt underneath in-flight XHRs.

**Contract:** `renderPhotos()` **skips the rebuild while `data-state` is `preparing` or
`uploading`**, and sets a flag when it does. On batch settle, if the flag is set, it renders once and
clears it. In every settled state (`idle`, `partial`, `success`, `refused`, `failed`, `full`) the
rebuild runs normally and reads from the batch model, so nothing is lost.

Because this phase writes zero `data-i18n` attributes, a skipped render leaves the control wholly in
the previous language rather than half translated. The section heading and lede do switch, since
they are static markup from phase 1. That inconsistency is bounded to the seconds a batch is in
flight and is the correct trade against tearing down live uploads.

## The Album Component System

### Markup contract

```html
<p class="album__head">14 submissions on record.</p>

<div class="album">
  <a class="album__tile" href="{publicUrl}" target="_blank" rel="noopener" aria-label="Open the photograph submitted by Sofia.">
    <span class="album__frame">
      <img src="{publicUrl}" loading="lazy" decoding="async" alt="">
    </span>
    <span class="album__by">Sofia</span>
  </a>
</div>
```

- **`alt=""` on the image and `aria-label` on the anchor.** The photograph has no describable
  content the site knows about, so an invented alt string would be a lie. The anchor's accessible
  name is the whole meaning: what it opens and whose it is. With `aria-label` set, the visible
  caption is not announced twice.
- **The `aria-label` string carries `{name}` and is therefore written by `renderAlbum()`**, set with
  `setAttribute`, never with a markup string.
- **`target="_blank" rel="noopener"`**, matching every other outbound anchor in the codebase. This is
  the deliberate non-lightbox (D-10): the browser's own image viewer already gives pinch zoom, save
  and share for zero code and zero bytes, and a half built lightbox would be worse than the native
  one. V2-06 defers the real thing.
- **`loading="lazy"` and a reserved box.** `.album__frame` carries `aspect-ratio: 1 / 1` and a
  `--surface` fill, so the box exists before the image does and nothing below it moves as the grid
  streams in. Same no-reflow guarantee phase 2 gave the map slot.

### The `storage_path` allowlist (NEW, security relevant, and it also cleans the album)

`renderAlbum()` renders **only** rows whose `storage_path` matches the D-20 shape:

```
^\d{4}-\d{2}-\d{2}/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\.jpg$
```

Non-matching rows are skipped silently and are not counted in `.album__head`.

Two things this buys:

1. **A database-supplied string stops being able to steer a URL.** The path is concatenated into
   both `href` and `src`. It cannot introduce a scheme, because it is appended after a fixed prefix,
   but without the allowlist it could carry traversal segments, a query, or a fragment. The regex
   removes the question rather than answering it.
2. **The album is clean on day one.** The research session left five `ZZTEST DeleteMe` rows behind
   at `zz-research/limit-N.jpg`, which `public.album` returns today. They do not match the shape and
   therefore never render, before the owner's cleanup rather than after it.

**The regex and `storagePath()` are coupled and must change together, in the same commit.** A path
shape change that lands without the regex change makes every new photograph invisible. Say so in a
comment on both.

### Album states

| State | `.album__head` | Grid |
|---|---|---|
| Fetching | `photos.album.loading` ("Retrieving submissions.") | absent |
| Populated | `photos.album.count.one` or `photos.album.count.many` with `{n}` | rendered, newest first (D-09) |
| Empty | `photos.album.empty` ("No submissions on record.") | absent (D-13) |
| Fetch failed | the whole album block is absent, head included | absent (D-14, silent) |

**There is no skeleton grid, and that is a decision rather than an omission.** A skeleton of six grey
squares is a fabricated claim about content the site does not have yet: the album can hold zero
photographs or two hundred, and promising a specific number of tiles is the same class of lie as a
fake progress bar, which this project has already refused twice. The honest loading state is one
line of text in the slot the register line occupies in every other state, so the only thing that
arrives when the fetch resolves is the grid, below it, growing the page downward into empty space.

**The album failing to load is silent and the upload control still works** (D-14). The two are
independent: a guest can submit evidence without being able to read the register. This produces one
apparent contradiction worth naming: a guest can see "1 photograph is on record" from the write
while the album read fails and shows nothing. That is honest. The status line is the site's claim
about a write that succeeded; the album is a separate read that did not.

**No polling** (D-12). The album refetches after a successful upload and on nothing else.

### 4. The eight control states (`.uploader[data-state]`)

| `data-state` | Button | Status line (`role="status"`) | Alert line (`role="alert"`) | Queue |
|---|---|---|---|---|
| `idle` | enabled, `photos.cta` | hidden, box reserved | hidden | absent |
| `preparing` | disabled, `aria-busy` | `photos.status.preparing` with `{i}` and `{n}` | hidden | visible |
| `uploading` | disabled, `aria-busy` | `photos.status.uploading` with `{i}` and `{n}` | hidden | visible |
| `success` | enabled | `photos.status.done.one` or `.many` | hidden | visible, all rows `done` |
| `partial` | enabled, plus the retry button | `photos.status.partial` with `{ok}` and `{bad}` | the failure and refusal sentences | visible, mixed |
| `refused` | enabled | hidden | the refusal sentence | visible, all rows `refused` |
| `failed` | enabled, plus the retry button | hidden | the failure sentence | visible, all rows `failed` |
| `full` | absent, whole `.uploader` replaced by the quota panel | absent | absent | absent |

**`validating` is deliberately folded into `preparing`.** A validation pass over five `File` objects
is sub-millisecond, so a distinct visible state would be a flash, and research Pattern 3 says as
much in its own table. Validation *results* are rendered as row states, which is where a guest can
actually act on them.

Two rules that are easy to violate, both inherited from phase 3's form:

- **`uploading` must always terminate.** The XHR wrapper wires `onload`, `onerror`, `onabort` and
  `ontimeout`, all four. Three of four is a control that spins forever on the fourth. `sbRequest`
  learned this the hard way and its comment at `app.js:1268-1286` records it; the XHR wrapper does
  not inherit that invariant and owes it separately.
- **`failed` and `refused` must not clear the selection.** The batch model holds the `File` objects.

**The success moment is a state change in the section body, and nothing else.** No toast (D-11 of
phase 3 reserves `toast()` for incidental confirmations). No focus move: phase 3 moved focus to the
success panel heading because the form was destroyed, but here nothing is destroyed and stealing
focus would fight a guest who is about to pick more photographs. **No programmatic scroll**, for the
same reason: a scroll the guest did not ask for moves the target out from under a thumb. The status
line, the ticking remaining count and the guest's own photograph appearing at the top of the album,
directly below the control, are the confirmation.

### 5. The quota refusal (highlighted design item, D-19 and D-23)

**This is the phase. The roadmap's done-when sentence ends here.**

It is not an error, it is not an apology, and it is not a disabled button with a tooltip. It is the
course closing a file, and it is the punchline of a lede that has been on the page since phase 1:
*"Maximum five per person, which is a limit chosen to protect everyone."*

Composition, replacing the whole of `.uploader`:

1. `h3.sub-h`, `photos.full.title`. **"Documentation complete"**, not "Limit reached". The register
   is the difference between the joke landing and an error message wearing a costume: hitting five
   is a course requirement satisfied, not a wall hit.
2. `p.panel__lede`, `photos.full.body`. **"Five photographs are on record in your name. The limit
   protects everyone, and at five you are protected."** That second clause is the punchline the lede
   set up, and it is written natively in all three languages rather than translated.
3. Nothing else. No button, no queue, no remaining count reading zero, no "contact the host" line.
   A zero in the remaining-count field would be a number where a joke should be.

The album stays below it, unchanged. The guest can still look at the evening; they simply cannot add
to it.

**No `tabindex` and no focus move on this panel.** It is reached in two ways. On page load it is
simply the state of the section, which is a page state and not an event. Mid-batch it is reached
after the alert line has already announced the refusal assertively, and moving focus as well would
announce the same fact twice, which reads as a stutter. The panel swap is the 220ms opacity
transition every body swap uses.

### 6. The three ways the refusal is reached, and the copy each one needs

| Path | What the guest sees |
|---|---|
| **At render**, stored count is already 5 | Body E directly. Just the punchline. |
| **Mid-batch overflow** (D-15): two remaining, five picked | The first two upload normally. The last three render as `refused` rows carrying `photos.refuse.extra` as their reason, the alert line carries `photos.refuse.extra` with `{n}`, and when the batch settles the control flips to body E. **The refused files are named in the queue rows**, which is where D-15's "named in the refusal message" requirement is honoured, and it is more readable than cramming three file names into one sentence. |
| **Server refusal** (`P0001`) after a local count drift | The bytes already went up, so the row's reason is `photos.refuse.server`: **"The register already holds five in your name. This one was not added."** It must not say the upload failed, because it did not; the submission was declined. The client sets its local count to five (D-19, self-healing) and the control flips to body E. |

`P0001` is treated as "you are at five" unconditionally and is **never retried with a fresh path**.
The trigger is `before insert`, so it fires ahead of the unique constraint and a guest at five sees
`P0001` for a path collision too. A retry loop there would upload bytes forever.

## Motion Contract

MOTION_INTENSITY **3** (D-28). Eight motion decisions exist and **four of them are refusals.** Every
animation is `transform` or `opacity` only. Every one ships its `prefers-reduced-motion` fallback
**in this phase** (D-29), joining the existing blocks at `styles.css:813` and `styles.css:1824`
rather than starting a third.

| # | Motion | Duration / easing | Purpose (one sentence) | Reduced-motion fallback |
|---|---|---|---|---|
| 1 | `.queue__fill` `scaleX` | 140ms `linear` per progress tick | Reports real bytes moving, which is the whole of PH-05. Linear, because the underlying quantity is linear and easing a real measurement makes it lie. | **`transition: none`, and the bar keeps updating in steps.** The bar is NOT removed and NOT parked, unlike `.sweep`. It carries information rather than atmosphere, and a guest who prefers reduced motion still needs to know their photograph is moving. This is the deliberate opposite of the `.map-wait__bar` reduced-motion rule and the distinction is the reason both rules exist. |
| 2 | Button `:active` scale to 0.97 | 140ms `--ease-out` | Confirms the interface heard a cold thumb. | Global rule collapses the transition to 0.01ms. Feedback survives as an instant state change. |
| 3 | Album tile `:active` scale to 0.98 | 140ms `--ease-out` | Same job at a much larger box size. | Global rule, same. |
| 4 | Body swap (`idle` to `full`, `closed` to `idle`) | 220ms `--ease-out`, **opacity only** | Prevents a hard cut at the moment the phase's headline events land. | Global rule collapses to 0.01ms: an instant swap. Correct and honest. |
| 5 | Album tile reveal on load | **Refused, deliberately.** D-28 permits it; this spec declines. | A staggered fade on a lazy-loaded grid animates forever as a guest scrolls, which is ambient motion and phase 5 owns that (DSG-04). At two hundred tiles it is two hundred animations competing with image decode on a phone on party wifi, and the reserved `--surface` box resolving into a photograph is already a visible change. | n/a. Phase 5 may add it as part of the arc, with this refusal on record so it reads as a decision reopened rather than an omission noticed. |
| 6 | Queue row appearance | **Refused, deliberately.** | Rows appear the instant the guest picks. Animating a list the guest just created delays information they are waiting for, and a stagger across five rows is a quarter second of nothing at the exact moment they want to know their files were seen. | n/a |
| 7 | Album head text change | **Refused, deliberately.** | The count changing is a text change, which is neither `transform` nor `opacity`, and a crossfade on a number is phase 3's refused count-up wearing a hat. | n/a |
| 8 | Progress bar shimmer, stripes or pulse | **Refused, deliberately.** | Decoration on top of a real measurement. If the bar is moving, the movement is the signal; if it is held at 0.92, the state word says why. Either way a shimmer adds nothing and is the reflex treatment. | n/a |

**Explicitly refused, so phase 5 knows these were considered rather than forgotten:** success
confetti and particles, a drawn checkmark or tick, a skeleton shimmer on tiles or on the grid, a
lightbox transition, a hover lift or shadow growth on tiles, a masonry reflow, and any height
animation on the body swap. Height is neither `transform` nor `opacity`.

**No `transition: all` anywhere. No `ease-in` on any UI element. No keyframes on anything a guest can
retrigger rapidly.**

### Inherited interpretation, recorded rather than smuggled

DESIGN-BRIEF.md says "animate `transform` and `opacity` only". This phase transitions `border-color`
and `color` on hover, and `background` and `color` on the disabled button. That is the interpretation
phase 1 shipped and phases 2 and 3 kept: motion is `transform` and `opacity`, and interactive colour
feedback is a separate, established category. Recorded so the checker does not flag it and nobody
quietly widens it into layout-property transitions.

### Third-party runtime surfaces touched by this phase

Neither is a component registry, but both are third-party endpoints reached from the page and they
are recorded here rather than left off the sheet.

| Surface | Origin | Mitigations |
|---|---|---|
| Supabase Storage, write | `POST {url}/storage/v1/object/party-photos/{path}` | Publishable key in `apikey` only; a `Bearer` header carrying this key format is rejected outright and must never be sent. `Content-Type: image/jpeg` set explicitly. `cache-control: max-age=31536000` set, which turns every album image from `no-cache` into a year-long cache on congested party data. No `x-upsert`, ever: overwriting is structurally impossible because no update policy exists, and sending it achieves nothing except a confusing error. Unconditional 60s timeout with all four terminal handlers wired. |
| Supabase Storage, public read | `GET {url}/storage/v1/object/public/party-photos/{path}` | No key, no headers, `Access-Control-Allow-Origin: *`. The path is validated against the D-20 shape before it is concatenated into `href` or `src`. |
| Supabase PostgREST | `{url}/rest/v1/photos`, `{url}/rest/v1/album` | `Prefer: return=minimal` on the insert, never `return=representation`, which answers 401 and does not write the row. Reads go through `public.album` and never through `public.photos`. Errors branched on `code`, never on `message`, and no `message` string is rendered into the page. |

**The attack surface this phase adds, stated plainly:** a guest's stored `name` is rendered into
every other guest's browser through the album caption, exactly as phase 3's attendee list does. The
`public.album` view truncates to the first token server side but does not sanitise. The mitigation
is absolute and non-negotiable: every caption, every `aria-label` and every album value is built with
`document.createElement` plus `textContent`, or set with `setAttribute`. No `innerHTML`, no template
string, no `insertAdjacentHTML`, anywhere near `first_name` or `storage_path`.

**Nothing this phase adds may hand out a `guest_id` or a full name** (D-25). No `guest_id` reaches a
filename, a URL, a `data-` attribute or the DOM. `public.album` does not carry the column, so it is
not merely unreadable, it is not addressable. Phase 3's amend function is only safe while this holds.
