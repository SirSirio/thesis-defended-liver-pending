<objective>
Close gap 1 of `03-VERIFICATION.md`: the row level rules publish the credential that section 8
created.

Section 8 changed what a `guest_id` **is**. Before this phase, holding one bought nothing.
After it, `amend_enrollment` is `security definer`, accepts `p_guest_id` as its only credential,
and will rewrite a name, a guest count, a note and the withdrawn flag on the matching row. A
`guest_id` is now a password (D-35). Section 3 has been handing that password out since phase 1,
through a policy that was harmless when it was written: `anon can view album` is
`to anon using (true)` over a table carrying `guest_id` and a full unsplit `name`. Probed live in
the verification, `GET /rest/v1/photos?select=*` answers **HTTP 200** to the publishable key. The
table is empty today, so this is a defect and not an incident. Phase 4's first upload turns it
into one.

Two smaller things stand in the same file. `anon can amend own enrollment` grants anon UPDATE on
every row with any values, is dead code since D-35 replaced its purpose, and is held inert only by
the unrelated absence of a SELECT policy: adding any SELECT policy, or clicking Supabase's
one-click read-access template, converts it in one step into unauthenticated mass rewrite. And the
database accepts five times the guest count `config.js` permits (D-30), summed straight into the
head count the host buys food against.

Purpose: this is the gap that arms rather than fires, and it must land before phase 4 starts.
It is also the phase's second one-way door: the photos read path is a published contract, and
phase 4 will be written against whichever shape is standing when it begins.

Output: `supabase/schema.sql` with the read path closed and re-opened through a projecting view,
both over-broad policies gone, the bounds reconciled, the false security claim corrected; a
one-line comment in `config.js`; an updated `COVERAGE.md`; and a live probe that proves the new
state on the wire rather than in the file.
</objective>

## Assumption delta decision

**Delta kind: pluralization.** The photos read path gains a second representation where there was
one: the table and a projecting view.

**Decision: promote.** `public.album` becomes the primary and only read surface for the album, and
`public.photos` is demoted to a write-only detail for the anonymous role. Add-alongside is
rejected because the thing being added alongside is the defect itself: leaving the table readable
leaves the credential published, and the view would then be an alternative rather than a boundary.

Reasoning: phase 4 has not been written, so there is no existing consumer to migrate and promote
costs nothing that add-alongside saves. This is the same shape the file already uses for
`enrollments` and `attendees`, so it introduces no new idea, only a missing application of one.
Recorded here rather than deferred because the decision is cheap now and expensive after phase 4
has a read call site.
