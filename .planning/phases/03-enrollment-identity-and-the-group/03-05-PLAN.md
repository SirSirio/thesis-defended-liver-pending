<objective>
Give a guest the two things a registration owes them: the ability to change it, and the ability to
leave. Both go through the function plan 03 added, because the update this project would naturally
have written touches zero rows and reports success.

Purpose: this closes the phase's last behavioural requirement and its most delicate one. Withdrawing
is the moment a guest is most likely to be manipulated by an interface, and the design decision here
is that leaving is exactly as easy as joining: one named confirmation, no timer, no offer to stay,
no second ask. The two specification gaps the UI probe found both live on this surface, and neither
is closed by hand-waving: a withdrawal with no in-flight state and no failure state is the exact
silent-success failure the whole schema change exists to prevent.

Output: the edit path, the two step withdrawal with a defined state between tap and response and a
defined state for every way it can fail, the withdrawn body, the forget control, and the last 14
copy keys.
</objective>

## The two unresolved UI considerations, and what this plan does about them

Both are on the withdraw confirmation (E5) and both stay `unresolved` in the lift by rule. They are
recorded here as explicit planner assumptions, and task 2 implements the resolution rather than
leaving them as prose.

| Row | The gap, stated | The assumption this plan proceeds on |
|---|---|---|
| **E5 loading, unresolved** | The spec defines the two step confirmation but no in-flight state for the amend call it fires. The confirm control has no defined treatment between tap and response, and the phase's 12 second abort contract is not stated to apply here. | That the confirmation borrows the form's existing submitting grammar rather than inventing a second one: the confirm control disables, its label swaps to the existing submitting label, the busy attribute is set, and the same 2px sweep bar pins to the top of the confirmation block. No new component, no new copy key, and the same unconditional abort, because a withdrawal that hangs is worse than one that fails. |
| **E5 error, unresolved** | The spec covers the not-migrated case but not a withdrawal that fails on the network or comes back having touched zero rows. A withdrawal that silently does nothing is the exact failure mode the schema change exists to prevent. | That three outcomes are distinguished and none is silent. A row count of 1 is a real withdrawal. A row count of 0 means storage and the database disagree about this guest id, so the honest response is to correct the local state and show the withdrawn body, because the database holds no registration for them. Not recordable, whether from the missing function or from a failed network, lands on the existing amend-pending line in place, which already says the change was not recorded and the registration stands. That line is reused rather than a new key written, because the phase's key budget is 42 and its wording is true in both cases. |

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser storage to the amend function | The guest id read from storage is the only authorisation the function has. Anyone holding it can amend that registration. |
| the anonymous role to a definer function | The function runs with its owner's privileges. This plan is its only caller. |
| a guest's stated intent to the database | A withdrawal is a claim the interface must not confirm until the database has confirmed it. |
| the device to the next person holding it | A phone handed to someone else still carries the previous guest's identity until it is removed. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-27 | Repudiation | A withdrawal reported as done while the database still counts the guest | high | mitigate | The phase's signature failure mode, and the reason the schema changed at all. Every branch reads the integer row count and the error code, never a status code. A not-recordable answer leaves the registration intact and says so; only a confirmed answer mounts the withdrawn body. Gated on the enrolled flag being written before that body is ever mounted. |
| T-03-28 | Denial of service | A withdrawal request that hangs with no in-flight state | high | mitigate | The first of the two specification gaps, and it is closed rather than noted. The same unconditional abort every other write carries, plus a visible in-flight treatment borrowed from the form so no second loading vocabulary is invented. The block always terminates in a defined state. |
| T-03-29 | Tampering | Amending or withdrawing someone else's registration with a stolen guest id | medium | accept | Unchanged from the trade already recorded in the shipped schema: anyone who knows a guest id can amend that registration, the id is 122 bits from a CSPRNG, and it never appears on the page, in a URL or in a shareable link. It would not be the right trade for anything that mattered. |
| T-03-30 | Information disclosure | A shared phone leaking one guest's identity to the next person holding it | medium | mitigate | The forget control removes every key this phase writes, from both storage and the in-memory map, and is reachable from the returning view and from the withdrawn body.
