<objective>
Close gap 2 of `03-VERIFICATION.md`, and the two warnings the verification's truth table names as
real defects rather than review noise.

`doWithdraw` is the function 03-05 was written for, and its header comment claims two things:
"the block always terminates somewhere defined", and "there is no path here where the interface
tells somebody they have withdrawn while the database still counts them". Both are false, and
they are false for one reason. `setFormState` disables the whole form because the form *is* the
whole body, so nothing else is reachable. `setWithdrawState` copied that shape onto a box that is
a sibling of three live controls, each of which calls `refreshEnrollmentState()` and clears
`#enrol-body` outright. Tap Confirm withdrawal, then tap any of them, and the request is still
out while the box it belongs to has left the document.

Three things fall out, all reachable at a desk. The failure branch renders into a detached
subtree and the guest gets no signal of any kind, which is the exact silent-failure class this
phase was built to eliminate. The success branch writes `store.set('enrolled','0')` after
`forgetIdentity()` cleared it, leaving the residue `identity.clear()` says a guest asked to have
removed. And an edit started mid-withdrawal races a second RPC carrying `p_withdrawn:false`
against the first carrying `true`, so the device and the database can disagree permanently.

Two more, in the same family. `doWithdraw`'s pending branch never sets `amendPending`, so the
not-recordable explanation evaporates on the next render and the Withdraw button comes back
(WR-04). And a network failure lands in the same terminal branch as a missing database function,
replacing the only way to withdraw with a paragraph, with no retry, on exactly the mobile-data
profile this phase was designed for (WR-05).

Purpose: this gap falsifies an invariant the phase wrote down for itself, in the one request the
same file calls "the one request that most needs to be believed". It is the second-highest risk in
the phase and it is entirely a code fix.

Output: `app.js` with the withdrawal isolated from its panel, both wire-layer termination holes
closed, and the two stale-write races that share the same shape closed with it.
</objective>

## How every gate in this plan is run

There is no test runner in this project and there will not be one: vanilla static site, no build
step, no npm, deployed on push. The established method, set by plan 03-06 and recorded in
`03-DEVICE-PASS.md` Table G, is to slice the shipped function out of `app.js` by brace matching
and run it in a fresh Node process with stubs standing in only for the browser objects it closes
over. **No branch condition is ever re-typed**, so a change to `app.js` changes the gate result.
That is the whole reason the technique is used rather than asserting on source text.

Every gate below runs as a single `node -e` invocation from the repository root. If a scratch file
is needed it lives outside the repository tree and is deleted afterwards; **no file is added to the
repository**. The prohibition on `eval` and `new Function` is a rule about shipped guest-facing
source, not about a throwaway gate process, and 03-06 set that precedent.

Each gate states the intent it asserts and why the shipped implementation cannot satisfy it. This
phase shipped seven gates whose expectation was read off the code they were testing, and the
verification calls that the phase's defining lesson. A gate that only proves the code does what
the code does is worth less than no gate, because it reads as coverage.
