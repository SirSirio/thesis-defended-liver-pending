<objective>
Prove the whole spine of this phase on one path, end to end, against the live database: a guest
opens the page, types a name, chooses how many people they are bringing, optionally writes a note,
submits, the row lands in `public.enrollments`, the form is replaced by a registration receipt, and
the nudge bar that has never rendered on any device switches itself on. Reloading shows the guest
their own registration instead of an empty form.

Purpose: this is the tracer. It touches every layer this phase modifies except the database schema,
deliberately, because `POST /rest/v1/enrollments` works against the live project today and the
schema re-run is an owner action that must not gate a guest's ability to register (D-36). If the
architecture is wrong, it is wrong after one commit rather than after ten.

Output: the identity module, the request helper, the form component system in CSS, the form itself,
the four submit states, the success receipt, the returning-guest view, and the validation and
accessibility layer that makes the form usable with a thumb and with a screen reader.
</objective>

  <action>
    Extend the existing `store` object in place rather than replacing it. Add an `ok` member,
    computed once by writing and removing a probe key inside a try, and a `mem` object. `set` writes
    to `mem` unconditionally and then attempts storage, dropping `ok` to false on a mid-session quota
    failure. `get` prefers storage when `ok` and falls back to `mem`. Add `remove`, which deletes from
    `mem` and attempts storage removal. Preserve both existing invariants exactly: the `c03102.`
    prefix is applied inside the wrapper and callers pass bare keys, and `set` still returns a
    boolean. Writing to `mem` unconditionally is what makes the private-browsing path work; a `mem`
    that is only a fallback for a failed write goes stale after the first successful storage write.

    Add `newGuestId()`. Feature detect with `typeof crypto !== 'undefined' && typeof crypto.randomUUID === 'function'`, not with an `in` test, because the crypto object itself is absent on insecure
    origins. Fall back to `crypto.getRandomValues` over a 16 byte array with the version and variant
    bits set and the bytes formatted as a real v4 string, because the column is typed uuid and a
    malformed one returns 400 with code 22P02. Return null when there is no crypto at all, never a
    pseudo-random string: a colliding id produces a confusing 409 for a guest who has never
    registered, and null lands cleanly in the unconfigured branch.

    Add an `identity` module over `store` with `get`, `save` and `clear`, reading and writing the
    keys `guest_id`, `name`, `extra_guests` and `note` alongside the phase 1 keys. `enrolled` is

    `app.js:1087` compares against that exact string. Do not rename or repurpose `lang`, `enrolled`
    or `wa_joined`; live guests already carry them on their devices.

    Add `sbConfigured()`. Use the identical expression `enrollmentReady()` uses at `app.js:1166`,

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| guest keyboard to database | A guest types `name` and `note`. Both are stored. `name` is the first untrusted input this project has ever persisted. |
| database to every other guest's browser | A stored first name is rendered into the attendee list on other devices. The `attendees` view truncates to the first token; it does **not** sanitise. |
| database to the same guest's browser | The stored name is rendered back into the receipt and the returning greeting. |
| browser storage to the page | `localStorage` values under the `c03102.` prefix are attacker-writable on a shared or compromised device. |
| publishable key to the public | The key ships in `config.js` in a public repository, by design. Row level rules are the only boundary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-01 | Tampering | Stored `name` rendered into the receipt, the greeting and later the attendee list | high | mitigate | Every guest string reaches the DOM through `createElement` plus `textContent`. Gate: `grep -cE '\.innerHTML[[:space:]]*=' app.js` returns 0, asserted in both tasks. No template string and no markup insertion anywhere near `name` or `note`. |
| T-03-02 | Tampering | `note` and `name` length and range bounds | medium | mitigate | Bounds enforced in the browser for the message and independently by the database `check` constraints for the truth. A limit that exists only in JS is a suggestion. |
| T-03-03 | Spoofing | Guessing another guest's `guest_id` to amend their registration | medium | mitigate | 122 bits from a CSPRNG. `Math.random` is banned by gate. The fallback builds a real v4 rather than a random hex string. Feature detection is by function type, not by property presence, because the crypto object is absent on insecure origins. |
| T-03-04 | Information disclosure | PostgREST error text reaching a guest | medium | mitigate | Branch on the `code` field only. Gate: no `message` property is read into the page, and zero console calls exist in `app.js`. Those strings leak table and constraint names. |
| T-03-05 | Information disclosure | The free-text `note` becoming readable by anyone but the host | high | mitigate | Structural, not enforced in JS: no SELECT policy exists and this plan adds none. Both read-back preferences on the insert are banned by gate, because either would require the read policy that does not exist. |
| T-03-06 | Denial of service | A bored guest enrolling four hundred people | medium | accept | Honestly scoped (D-30). The unique constraint caps one browser at one row, the submit control locks for the request, and both bounds are enforced twice. A determined person clearing storage in a loop can still create rows, and **no amount of client-side code changes that on a static site with a public insert policy.** Documented rather than papered over. The owner's recourse is the dashboard. |
| T-03-07 | Repudiation | A guest's registration silently not happening while the UI reports success | high | mitigate | The project's signature failure mode: a blocked read answers with an empty array and a blocked delete answers 204, so both look like success. This plan proves the write by inserting and then reading back through the only path allowed to see it, and bans the update shape that the live probe showed touches zero rows. |
| T-03-08 | Elevation of privilege | Reading enrollment state from the database rather than from storage | medium | mitigate | Banned by design and by gate: a read of the raw table returns an empty array forever, so code that asks it whether a guest is enrolled concludes no, permanently. Storage is the sole source of truth. |
| T-03-SC | Tampering | Dependency supply chain | low | accept | No package manager, no lockfile, no build step, no `package.json`, and nothing installed by this plan or by this phase. `03-RESEARCH.md` §Standard Stack records the Package Legitimacy Audit as not applicable for exactly this reason. The only third-party runtime surface is the PostgREST endpoint already wired in `config.js`. |
