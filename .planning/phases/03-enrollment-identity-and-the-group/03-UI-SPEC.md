# Phase 3 — UI Design Contract

> Visual and interaction contract for the enrollment form, identity, the success handoff,
> the returning-guest view, social proof, the `#wa` section, and switching the nudge bar on.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This phase builds the site's first form.** `styles.css` contains zero `input`, `label`,
> `textarea`, `select` or `fieldset` rules today (verified, research §G1). Everything under
> `## The Form Component System` is NEW. Everything under Design System, Spacing, Typography
> and Color is read out of the deployed `styles.css` unless a row is marked **NEW**.
>
> **This phase adds zero new type sizes, zero new weights, zero new families and zero new
> colour values.** Every value below already ships. That is a deliberate constraint, not a
> coincidence: a form is where an ad-hoc design system gets invented, and this contract
> exists to stop that happening.

### The physical scene that governs every decision

A guest is on a mid-range phone, on mobile data, at night, possibly outdoors, holding the
phone in one hand and using one thumb. The roadmap's done-when sentence is **"a guest on a
phone enrolls in under 10 seconds"**. That sentence outranks every aesthetic decision in this
document. Where this spec breaks a design-taste guideline, it is because of it, and the break
is stated rather than smuggled.

### Category-reflex check (anti-slop, run at both altitudes)

- **First-order reflex** for "RSVP form on a party site": a centered card, rounded inputs, a
  pill-shaped "Count me in!" button, a green checkmark, confetti on success, an emoji
  somewhere. **Refused.**
- **Second-order reflex** ("an RSVP that is not a party RSVP"): the premium SaaS signup.
  Floating labels, a soft-shadowed card on a subtly gradient panel, 12px radii, a gradient
  CTA, a spinner, a toast. This is exactly what the two routed skills reach for.
  **Refused.** See `## Routed-Skill Conflicts` for the itemised list.
- **What ships instead:** the form is **the course fact table with editable cells**. It reuses
  the exact grid geometry of `.facts__row` (label column left, value column right, hairline
  between rows, single column below 640px), so a guest who read the course facts at the top of
  the page meets the same object again, now with their own record in it. The success panel is
  a **registration receipt** in the same `.facts` grammar. The attendee list is a **class
  list**, alphabetical, comma separated, not a social feed. **Zero icons anywhere in this
  phase.** No checkmark, no chevron, no spinner glyph, no caret drawn by hand.
- **Why that clears both altitudes:** it reads as the registration slip on page six of a
  course description, which is neither reflex, and it is also the fastest possible answer for
  the 10-second target, because it introduces no component grammar the guest has to learn.

Inherited from `:root`, on a 4px base. **This phase adds no token.**

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| `--s-1` | 4px | Hint to error node |
| `--s-2` | 8px | Label to control (single column); control to hint; nudge clearance above the reserve |
| `--s-3` | 12px | Panel heading to its lede; textarea vertical padding |
| `--s-4` | 16px | `.field` vertical padding; control horizontal padding; between stacked `.subtle-action` rows |
| `--s-5` | 24px | Grid gap between label and control columns; panel lede to receipt; reserved error-line height |
| `--s-6` | 32px | Form to `.enrol-actions`; receipt to primary CTA |

| `--s-8` / `--s-9` / `--s-10` | 64 / 96 / 128px | Section block padding, inherited via `.section` |

than a spacing value.

### Spacing decisions specific to this phase

| Relationship | Value | Reason |
|---|---|---|
| `.field` vertical padding | `var(--s-4) 0` | Identical to `.facts__row`. The form must be the fact table, and the fact table's rhythm is 16px. |
| Label to control, single column | `var(--s-2)` | 8px. Tight enough that the pair reads as one object, which is what stops a guest at 320px reading the hint of the row above as this row's label. |
| Control to hint | `var(--s-2)` | Same reason, same side of the control. |
| Hint to error node | `var(--s-1)` | 4px. The error is a consequence of the control, not a sibling of it. |
| Reserved error line height | `min-height: var(--s-5)` (24px) | See Interaction States. The error box holds its space in every state so the submit button never moves under a thumb. Same no-reflow guarantee phase 2 gave the map slot and the map caption. |
| `.enrol-actions` top margin | `var(--s-6)` | 32px. Enough that the submit reads as an action rather than a fourth field. |
| Enrollment body to social proof | `var(--s-7)` | 48px, matching phase 2's sub-block rhythm. These are two separate answers to two separate questions. |
| Between stacked `.subtle-action` rows | `var(--s-4)` | 16px, on top of two 44px targets. Below 16px, two adjacent grey links are a mis-tap farm at 320px. |

**16px on every text control is a hard constraint, not a preference.** Any input with a
computed `font-size` below 16px makes iOS Safari zoom the viewport on focus and never zoom
back out. That single defect would cost more than every other decision in this document
combined. It is also a device-pass item (D-33).

**Segment digits are mono with tabular figures** for the same reason the countdown is: three
segments of equal width whose glyphs do not shift when the selection moves.

**No new uppercase micro-label is added by this phase.** The page-wide eyebrow count stays at
1 (the hero) against a budget of `ceil(8 sections / 3) = 2`. `.pending__t` is uppercase and is
rendered once by this phase (the ENR-12 branch), which is the same honest distinction phase 2
recorded: this phase **adds** none and **renders** one.

**Wrapping:** `.facts--record dd` carries `white-space: pre-wrap; overflow-wrap: break-word;`
so a note reads back exactly as it was typed, including line breaks, and a 60-character
unbroken name never pushes the page sideways at 320px. `.field__err` and `.field__hint` carry
`overflow-wrap: break-word`.

### The one new semantic this phase introduces

**`--rule` means structure. `--ink-faint` means editable.**

Every hairline that separates read-only information stays `--rule` `#2A2A2E`. Every boundary
around something the guest can type in or choose is `--ink-faint` `#6E6E73`. A disabled
control drops from `--ink-faint` back to `--rule`, which is the visual sentence "this is
information again, not a field".

This is not decoration. `--rule` on `--bg` is **1.37:1**, far below the 3:1 that WCAG 2.1
SC 1.4.11 requires for a control boundary, and an input outlined in `--rule` would be a
non-text contrast failure on the site's first form. `--ink-faint` clears it on both
backgrounds. Phase 2's orchestrator finding stands untouched: `--ink-faint` is 3.88:1 and
remains **banned for body text**. It is used here as a boundary, never as a glyph.

### Accent reserved for, in this phase, exhaustively

1. The fill of `.btn--primary` on the **submit** button. One filled accent button in the form.
2. The fill of `.btn--primary` on the **WhatsApp CTA** in the success panel, and on the
   **WhatsApp CTA** in the `#wa` section. These are two different sections, so the
   one-filled-accent-button-per-section-region rule holds.
3. The fill of the **selected** guest-count segment, which is the identical treatment
   `.langswitch button[aria-pressed="true"]` already uses for a selected segment on this page.
4. The inherited `.pending` left rule, in the ENR-12 branch only.
5. Nothing else. Not headings, not field borders, not the receipt, not the social proof block,

### The destructive-colour honesty note

The template asks for a distinct destructive colour. **There is not one, and there cannot be.**
DESIGN-BRIEF.md locks DTU red as the single accent and permits no second UI hue; the rest of
the DTU secondary palette is restricted to transient motion. So destructive and accent share a
hue by contract.

The differentiation therefore has to be carried by something other than colour, and it is:
the destructive control is the **only** ghost button on the page whose border and label are
`--accent-lit` at rest, it is the **only** control reached through a two-step confirmation,
and its label names the consequence in full ("Confirm withdrawal", never "Yes" and never
"OK"). Recorded as a constraint-driven deviation rather than an oversight.

### Discretion call: field order is Name, Guests, Note

1. Name is the required field and the fastest one, because `autocomplete="name"` fills it in
   a single tap on both platforms. Putting it first is most of the 10-second target.
2. Guest count is one tap, so it costs nothing in the middle.
3. The note is optional and the only field that costs typing. It goes last so a guest who does
   not want it reaches the submit button with their thumb already moving down the screen.

### Discretion call: guest count is a segmented radio group, not a stepper and not a select

`maxGuestsPerPerson` is 2, so the choice is `0`, `1`, `2`.

- **A stepper** (`−` `n` `+`) is three targets for a three-value choice, and its `−` control
  is disabled at the default value, which puts a disabled control on the happy path. Refused.
- **A `<select>`** is three interactions on iOS: tap, spin the wheel, tap Done. Refused as the
  default.
- **A segmented radio group** is one tap, shows all options at once, needs no open or close,
  and reuses the exact selected-state grammar `.langswitch` already ships. Chosen.

**The `<select>` is the documented overflow branch.** If the owner ever sets
`maxGuestsPerPerson` above 4, six or more segments no longer fit at 320px and the field
renders as a native `<select>` with options `0..max` instead. Both branches are specified
below. The threshold is `maxGuestsPerPerson <= 4` for segments.

**`maxGuestsPerPerson === 0`:** the whole field is absent from the form, not a one-option
control, and `extra_guests: 0` is sent. Zero-one-many, covered.

### Discretion call: `#wa` sits immediately after `#enrol`

1. The group is the second half of the registration act. A returning guest reading "Your
   registration" and then, one section down, "Course announcements" reads one continuous
   statement about their own status.
2. **On the day this phase lands the page order does not change at all**, because
   `whatsapp.inviteUrl` is `null` and the section ships with the `hidden` attribute set in
   static markup (WA-06, D-24, D-37).
3. The cost, once the owner supplies a link, is that `#location` moves one section further
   down. That is bounded: `#location` is reachable in one tap from the top nav and from a hero
   button, and the section itself is short by design.

**No topnav entry is added for `#wa`.** `styles.css:1215-1222` records that the topnav already
wraps at desktop and had to be tightened by a whole spacing step to fit six items. A seventh
would reopen a defect that was closed one phase ago.

### Discretion call: social proof lives inside `#enrol`, below the body

1. It is persuasion aimed at a control, so it belongs beside the control it is persuading
   toward.
2. **Below, not above, and the reason is layout shift.** The block arrives after an async
   fetch. Above the form it would push the form and the submit button down mid-interaction on
   exactly the connection profile this phase is designed for. Below the form it grows the page
   downward into empty space and can move nothing the guest is currently touching.
3. It gets no heading of its own. `.facts` labels its own rows, a 48px gap and the component's
   own `border-top` already separate it, and an `h3` would cost 48px of margin and a copy key
   to restate what "Expected attendance" already says.

## Touch Target Geometry

44px is the floor, not the target. These are pressed one handed, at night, possibly outdoors.

| Element | Fine pointer | Coarse pointer | Reason |
|---|---|---|---|
| Submit button | 52px | **56px** | The single most important control in the phase. Matches the phase 2 directions buttons, which are the page's other primary actions. |
| WhatsApp CTA, success panel | 52px | **56px** | Same standing. It is the phase's second headline action. |
| WhatsApp CTA, `#wa` section | 48px (inherited `.btn`) | 52px | Secondary reachability, not the moment. |
| Text input | 48px | **52px** | Matches `.copybtn`. A 44px input is a legal minimum, not a comfortable one. |
| Textarea | 96px min-height | 96px | Three rows at 16px / 1.5 plus padding. `resize: vertical` allowed, never `resize: none`. |
| Guest-count segment | 48px | **52px** | Matches the input it sits between, so the three field rows are one rhythm. |
| Select (overflow branch) | 48px | 52px | Same. |
| Edit / Register again / Confirm withdrawal | 48px (inherited `.btn`) | 52px | Secondary buttons. |
| `.subtle-action` (withdraw, clear identity, keep my registration) | text baseline | **44px inline-flex box** | The floor is correct here. These must be reachable and must not be inviting. |
| `.inline-link` "Change these details" | text baseline | 44px inline-flex box | Same. |
| Nudge CTA / close | 44px | 44px | Existing, unchanged. |

**Phone layout (`max-width: 480px`):** the submit button, both WhatsApp CTAs, the edit button
and the withdrawn state's "Register again" go `width: 100%`, mirroring the existing

640px the label sits in the left column and the control in the right, which is the CourseBase

**Control max-widths in the right column**, so a 1080px viewport does not produce an 800px
wide name field: name `max-width: 32ch`, textarea `max-width: 54ch`, segmented control

## The Form Component System

### Markup contract (one field, all three types share it)

```html
<div class="field" data-invalid="false">
  <label class="field__label" for="enrol-name" data-i18n="enrol.form.name.label">Full name</label>
  <div class="field__control">
    <input class="field__input" id="enrol-name" name="name" type="text"
           maxlength="60" required
           autocomplete="name" autocapitalize="words" autocorrect="off" spellcheck="false"
           enterkeyhint="next"
           aria-describedby="enrol-name-hint enrol-name-err">
    <p class="field__hint" id="enrol-name-hint" data-i18n="enrol.form.name.hint">As it should appear on the participant list.</p>
    <p class="field__err"  id="enrol-name-err"></p>
  </div>
</div>
```

Non-negotiable structural rules:

- **`<form id="enrol-form" novalidate>`.** `novalidate` suppresses the browser's own validation
  bubbles, which are unstyleable, wrongly registered, and rendered in the **browser's** language
  rather than the site's, which would break LNG-06 the first time a Danish guest with an English
  browser left the name blank.
- **Submission is bound to the `submit` event**, never to a click handler on the button, so
  Enter in the name field submits.
- **Zero `placeholder` attributes anywhere in this phase.** Placeholders are not labels, they
  vanish on input, and a placeholder is one more string whose contrast has to be defended.
- **The error node exists from first render and is empty when valid**, so `aria-describedby`
  is written once in markup and never added or removed. An empty node contributes nothing to
  the accessible description, so this is correct in the valid state too.
- **CSS styles `[data-invalid="true"]` on the wrapper, never `:invalid`.** `:invalid` matches
  a required empty field before the guest has typed a single character.
- **Every static string inside the form carries `data-i18n`.** `applyLanguage()` already
  sweeps `[data-i18n]` across the whole document including JS-injected nodes, so a language
  switch re-translates the form for free without rebuilding it.
- **Any string containing a placeholder token must NOT carry `data-i18n`.** The sweep would
  overwrite the substituted value with the raw template. `enrol.return.lede` (`{name}`) is
  written by `renderEnrollment()`, which runs after the sweep, exactly as `renderDeadline()`
  already handles `hero.deadline`'s `{date}`.
- **The form is built once and persists.** `renderEnrollment()` swaps `#enrol-body` only when
  the state changes. This removes research Pitfall 7 by construction: a language switch cannot
  destroy typed values or move focus, because it never rebuilds the form.
- **Guest input is only ever written with `createElement` + `textContent`.** Never `innerHTML`,
  never a template string. This is already the house rule (`app.js:246-249`) and this is the
  first phase where breaking it would be exploitable: a stored `name` is rendered into every
  other guest's browser through the attendee list.

### The three controls

| Control | Element | Attributes beyond the shared set |
|---|---|---|
| Name | `<input type="text">` | `maxlength="60"`, `required`, `autocomplete="name"`, `autocapitalize="words"`, `autocorrect="off"`, `spellcheck="false"`, `enterkeyhint="next"` |
| Guest count | `<div class="segset" role="radiogroup" aria-labelledby="enrol-guests-label">` containing one `<label class="seg">` per value, each wrapping a `.sr-only` `<input type="radio" name="extra_guests">` and a `<span>` | Value `0` carries `checked`. `aria-describedby` on the group points at the hint and error nodes. |
| Note | `<textarea rows="3">` | `maxlength="500"`, `autocapitalize="sentences"`, `enterkeyhint="done"` |

**Why `role="radiogroup"` + `aria-labelledby` instead of `<fieldset>` + `<legend>`:** a
`<legend>` inside a CSS Grid container has documented layout bugs in Safari, and every
workaround either duplicates the label string into two nodes or hacks the legend out of flow.
`role="radiogroup"` with `aria-labelledby` pointing at the same visible `.field__label` gives
byte-identical semantics, one string, one node, and no layout hack. The native `<input
type="radio">` children still supply grouping, arrow-key roving and `:checked` state for free.
Recorded as a deliberate substitution for the fieldset the phase brief named.

**Segment styling hook:** `.seg input:checked + span`, a sibling selector, **not**
`.seg:has(input:checked)`. `:has()` did not ship until Safari 15.4, which is the same browser
population that needs the `crypto.randomUUID` fallback. The whole control must not silently
lose its selected state on the exact devices this phase already knows about.

**Focus visibility on the segments is a required explicit rule.** The radio input is
`.sr-only`, so a `:focus-visible` outline painted on the input itself is a 1px clipped
rectangle nobody can see. The ring must be drawn on the adjacent span:
`.seg input:focus-visible + span { outline: 2px solid var(--accent-lit); outline-offset: 3px; }`.
Omitting this ships a control that is completely invisible to keyboard users. `.seg` needs
`position: relative` so the absolutely positioned `.sr-only` input is contained.

**The select branch keeps its native appearance.** Only `min-height`, `font-size: 16px`,
`color`, `background`, `border`, `border-radius` and `padding` are set. `appearance` is not
touched, no caret is drawn, and `<option>` rendering is left to the system. Same reasoning
phase 2 applied to native video controls: fighting a platform picker is pure failure surface,
and drawing a caret would mean either a hand-rolled SVG or a border-triangle hack, both of
which this project has refused.

### Validation timing (ENR-09, D-10)

| Trigger | Behaviour |
|---|---|
| `blur` on a field the guest never typed in and left empty | **Nothing.** MDN is explicit: do not set `aria-invalid="true"` on empty required elements until the guest attempts to submit. |
| `blur` on a field the guest typed in | Validate. Write the message, set `aria-invalid`, set `data-invalid` on the wrapper. |
| `input` on a field **already showing** an error | Re-validate, so the error clears the instant it is fixed and never appears mid-word. |
| `input` on a valid field | Nothing. |
| `submit` | Validate all. Populate every error node. Move focus to the **first** invalid control. Do not submit. |

The active error's copy key is stored on the control as `data-errkey` so a language switch
can re-render a currently visible error without re-running validation.

**Error strings are capped at 36 characters in every language.** At 320px, minus 48px of
`.wrap` padding, 14.5px IBM Plex Sans fits roughly 38 characters on one line. A two-line error
would defeat the reserved 24px error box and move the submit button, which is the exact
failure the reserve exists to prevent. The cap is a copy constraint and it is verifiable by
counting.

**No character counter on the note field.** `maxlength` stops typing at 500, a live-updating
count is a second thing moving on the screen while someone writes, and the counter would be
the only element on the page that changes on every keystroke.

## Interaction States

Every interactive element in this phase, across all eight states. Where a state is not
reachable, that is stated with the reason rather than a style being invented for it.

### 1. Text input and textarea (`.field__input`, `.field__textarea`)

| State | Treatment |
|---|---|
| **Default** | `background: var(--surface)`; `border: 1px solid var(--ink-faint)`; `border-radius: var(--r-sm)` (2px); `color: var(--ink)`; `font-size: 16px`; padding `0 var(--s-4)` (input) or `var(--s-3) var(--s-4)` (textarea). |
| **Hover** | `border-color: var(--ink-dim)`. 140ms `--ease-out`. Gated behind `@media (hover: hover) and (pointer: fine)`, so it never fires from a touch. |
| **Focus** | Global `:focus-visible`, unchanged: 2px `--accent-lit`, offset 3px, radius 2px. **No bespoke focus styling and no border colour change on focus.** The offset ring on a 52px box is unmissable, and a second focus signal would be the first place a bespoke form language starts. Recorded as a refusal. |
| **Active (pressed)** | **Not a distinct state for a text control.** Pressing a text field is focusing it, and the caret is the feedback. No style defined, deliberately. |
| **Filled** | **No distinct treatment, deliberately.** The typed value is the signal. A border or fill change on "has content" produces a form that looks half broken while it is being filled in, and it duplicates information the guest can already read. |
| **Disabled** (during `submitting`) | `background: var(--bg)`; `border-color: var(--rule)`; `color: var(--ink-dim)`; `cursor: not-allowed` on fine pointers. **No `opacity` anywhere**, because compositing the label down fails 4.5:1 (see Color). The guest can still read their own answers at 7.65:1 while the request is in flight, which is the whole point. |
| **Error** | Wrapper `data-invalid="true"`; control `border-color: var(--accent-lit)`, still 1px; `aria-invalid="true"`; the message appears in the reserved error box below. **Colour is never the only signal**: the message text below satisfies WCAG 1.4.1. No red fill, no icon, no shake. |
| **Loading** | **Not applicable.** A text field does not load. The form-level `submitting` state owns it. |

### 2. Guest-count segment (`.seg > span`)

| State | Treatment |
|---|---|
| **Default (unselected)** | `background: var(--surface)`; `border: 1px solid var(--ink-faint)`; `color: var(--ink)`; mono 16px weight 400; `min-height: 48px` / 52px coarse; radius 2px. Segments sit in a `repeat(N, 1fr)` grid with a `-1px` margin collapse so adjacent borders do not double. |
| **Hover** | `border-color: var(--ink-dim)`, fine pointers only, 140ms. |
| **Focus** | `.seg input:focus-visible + span` gets the global ring values explicitly (see above). Mandatory. |
| **Active** | `transform: scale(0.97)`, 140ms `--ease-out`, matching `.btn:active`. |
| **Selected** | `background: var(--accent)`; `color: #fff`; `font-weight: 600`; `border-color: var(--accent-lit)`. Identical grammar to `.langswitch button[aria-pressed="true"]`. Width does not change because the grid columns are `1fr`. |
| **Disabled** (during `submitting`) | `background: var(--bg)`; `border-color: var(--rule)`; `color: var(--ink-dim)`. The selected segment keeps its `--accent` fill so the guest can still see what they chose. |
| **Error** | **Not reachable by construction.** A radio group with a checked default cannot hold an invalid value. `enrol.err.guestsRange` exists for the select branch and for a tampered DOM only. |
| **Loading** | Not applicable. |

### 3. Submit button (`#enrol-submit`, built on `.btn.btn--primary`)

| State | Treatment |
|---|---|
| **Default (idle)** | `.btn--primary`, label `t('enrol.submit')`. 52px / 56px coarse, full width at ≤480px. |
| **Hover** | Inherited: background to `#B00000`, fine pointers only. |
| **Focus** | Global `:focus-visible`, unchanged. |
| **Active** | `transform: scale(0.97)`, 140ms. Inherited. |
| **Disabled** (during `submitting`) | `disabled` attribute set; label swaps to `t('enrol.submitting')`; `aria-busy="true"`. Fill drops to `--rule`, label to `--ink-dim` (7.65:1 on `--rule` composite is above 4.5:1). |
| **Loading** | The **2px `.sweep` bar pinned to the top edge of `.enrol-actions`**, spanning its width, `--accent-lit`, `translateX(-100%)` to `translateX(400%)` on a 1100ms `linear` infinite loop, drawn as a pseudo-element at 25% width inside an `overflow: hidden` strip. This is the same component and the same keyframe the map waiting state already uses, so the page has one vocabulary for "something is happening" rather than two. **No spinner glyph**, which would be a hand-rolled SVG, and no percentage, which would be a fabricated progress claim. |
| **Error** | The button itself does not carry the error. Label swaps to `t('enrol.retry')` and the `.form-alert` banner above it carries the message. |
| **Success** | The button is removed from the DOM along with the rest of the form. |

**Why the sweep bar and not nothing:** a completely static "Submitting" for up to 12 seconds
on bad mobile data reads as frozen, and D-08's whole point is that a guest is never left
guessing. Reusing phase 2's bar is consistency; inventing a spinner would be a second loading
language and an animation this phase would owe a reduced-motion fallback for while
communicating nothing the label does not already say.

### 4. The four submit states (ENR-10, D-11)

One attribute on the form drives everything. CSS reads it, JS sets it. No class juggling.

| `data-state` | Button | Controls | Body | Announced |
|---|---|---|---|---|
| `idle` | enabled, `enrol.submit` | editable | the form | no |
| `submitting` | `disabled`, `enrol.submitting`, `aria-busy="true"`, sweep bar visible | all `disabled`, values still readable at 7.65:1 | the form | no |
| `success` | gone | gone | **success panel** | yes, by moving focus to its heading |
| `failure` | enabled, `enrol.retry` | **editable, values retained** | form plus `.form-alert` | yes, `role="alert"` |

**`failure` must not clear the fields**, and the persistent-form contract above guarantees it:
the form is never rebuilt, so there is nothing to restore.

**`submitting` must always terminate.** The request helper's abort timer is unconditional and
its `catch` resolves rather than rejects, so no code path can leave the button locked.

### 5. The failure banner (`.form-alert`)

- A `<div role="alert">` that **exists in the DOM from first render**, `hidden`, and is
  unhidden and filled on failure. Many screen readers will not announce a live region that is
  inserted at the same moment its content is written.
- Position: directly **above** `.enrol-actions`, so the message and the retry button are one
  object under the thumb.
- Content: `enrol.fail.title` at 15.5px weight 600 in `--accent-lit`, then `enrol.fail.body`
  at 14.5px in `--ink-dim`. The body names the recovery and the fact that the answers survived.
- Visual: no border, no fill, no icon. It is a paragraph in the phase's destructive colour.
  A bordered red box here would be the only card on the page and would read as a browser error.
- `role="alert"` carries an implicit `aria-live="assertive"`, which is right for a failed
  submit and wrong for a field error. Field errors are **described** via `aria-describedby`,
  never announced. Two channels, two jobs.
- The existing `#toast` (`role="status"`, polite) is **not** used for the failure. Polite is
  the wrong urgency and the toast is a transient channel for a message the guest must act on.
- **Never render a PostgREST `message` string into this banner.** Those strings are English,
  unstable, and leak table and constraint names. Branch on `code`, map to a copy key.

### 6. The success panel (highlighted design item, D-23 and D-37)

This is the phase. The roadmap's done-when sentence lives here.

**It is a registration receipt**, not a celebration. Composition, top to bottom:

1. `h3.sub-h` with `tabindex="-1"`, `enrol.success.title` ("Registration confirmed").
   **Focus is moved to this heading the moment the panel mounts.** That is what announces
   success to a screen reader user whose focus was on a submit button that no longer exists,
   and it is what scrolls the new content into view for everyone else. The panel is **not**
   also wrapped in `role="alert"`: focusing it already announces it, and doing both produces a
   double announcement that reads as a stutter.
2. `p` lede, `enrol.success.lede`, `--ink-dim`.
3. `dl.facts.facts--record` with the guest's own submission read back:
   - **Name** → the trimmed name.
   - **Additional guests** → the number, or `enrol.record.guests.none` ("None") when 0. A bare
     `0` in a receipt reads as a missing value; `facts.location.tbd` already set the precedent
     for a worded value in this table.
   - **Note** → the note, `white-space: pre-wrap`. **The row is absent entirely when the note
     is empty.** No "n/a" filler, matching phase 2's practical-notes discipline.
   Echoing the note back is the answer to research Pitfall 8: the note is structurally
   unreadable from the database forever, so this is the only confirmation a guest will ever
   get that it arrived. It costs nothing, because it is already in storage per D-03.
4. `p` framing line, **reusing the existing `wa.body` key** rather than writing a new one.
   One message, one voice, and it is already the course-announcement-channel framing WA-05
   asks for.
5. **The WhatsApp CTA**, `a.btn.btn--primary`, `wa.cta`, 56px coarse, full width at ≤480px,
   `target="_blank" rel="noopener"`, sets `wa_joined` on click.
6. `a.inline-link`, `enrol.success.amend` ("Change these details"), 44px coarse box. Routes to
   the edit path for the guest who spots a typo one second after submitting.

**No withdraw control appears in the success panel.** Research §Pattern 4 is explicit: the
success panel and the returning view are near-identical in content and opposite in purpose,
and building them as one component with a flag produces a withdraw button at the instant of
celebration. They are two components that share one receipt.

#### The linkless success panel (D-37: this is the shipping state, and it was designed first)

`whatsapp.inviteUrl` is `null` and will be on the day this phase lands. With no link:

- Items 4 and 5 are replaced by **one line of body copy in `--ink-dim`**, sitting exactly
  where the button would be: `enrol.success.group.pending` ("The course group chat is not set
  up yet. The link appears here when it is."). It names the state and the next thing that
  will happen.
- It is **not** a `.pending` panel. A bordered placeholder panel inside the success panel is a
  nested card, which phase 2 already refused for the same reason, and `.pending__t` is an
  uppercase micro-label this phase has committed to not adding.
- It is **not** a disabled button. WA-06 says absent, not broken.
- Nothing else changes. Items 1, 2, 3 and 6 are unaffected, which is why the receipt had to be
  the panel's payload rather than a garnish: in the linkless state the receipt **is** the
  panel, and it is complete on its own.

#### Panel geometry

`.panel` has **no border, no fill and no radius.** It is a region, not a card. The only boxes
in the enrollment section are the input controls, and one panel wrapping a fact table that
already draws its own hairlines would be a nested card.

**The section height changes when the form is replaced by the panel.** Accepted, with the
mitigation stated: focus moves to the panel heading immediately, which takes the guest's eye
and the viewport to the new content deliberately. The change also follows a tap the guest
made, so a change is expected. No height animation, ever: height is not `transform` or
`opacity`.

### 7. The returning-guest view (ENR-05, ID-03, D-03)

Renders **entirely from `localStorage`, never from a fetch.** D-02 makes this the only possible
design and D-03 makes it the intended one.

1. `h3.sub-h`, `enrol.return.title` ("Your registration"). No `tabindex`, no focus move: this
   is a page state, not an event.
2. `p` lede, `enrol.return.lede` with `{name}` substituted: "Registered in the name of {name}.
   Nothing further is required." This is ID-03's greeting and D-18's proof that the site never
   asks a name twice. Written by `renderEnrollment()`, **not** via `data-i18n`, because it
   carries a placeholder.
3. The same `dl.facts.facts--record` receipt as the success panel. One component, two hosts.
4. `button.btn.btn--ghost`, `enrol.edit` ("Change your registration"). Ghost, not primary,
   because the correct action for a returning guest is nothing at all.
5. Below it, separated by `var(--s-6)`, two stacked `.subtle-action` links with `var(--s-4)`
   between them and 44px each:
   - `enrol.withdraw` ("Withdraw from the course")
   - `enrol.identity.clear` ("Forget my details on this device") — D-16's understated path for
     the guest who hands their phone to someone else.

**`.subtle-action` is `--ink-dim`, underlined, 14.5px. Deliberately not `--accent-lit`.**
`.inline-link` is red and draws the eye, which is right for a helpful jump and exactly wrong
for a control whose design goal is "reachable without inviting accidental taps". Grey and
underlined is discoverable, unambiguous, and does not advertise itself.

**Edit path:** tapping Edit re-mounts the form with `data-mode="edit"`, prefilled from storage,
submit label `enrol.update` ("Save changes"), plus a `.subtle-action` `enrol.cancel` ("Discard
changes") that returns to the returning view. Success routes back to the returning view with
`toast(t('enrol.updated.toast'))` — the one incidental confirmation D-11 assigns to `toast()`.

### 8. The withdraw confirmation (highlighted design item)

**Inline, two step, in place. No modal, no `confirm()`, no `<dialog>`.**

- `confirm()` is unstyleable, renders in the browser's language, and is the exact
  `alert()`-style pattern research listed as outdated.
- A `<dialog>` would be the only modal on the site, needs focus trapping, and is heavy for a
  party RSVP on a phone.

Behaviour: tapping `enrol.withdraw` replaces **that line in place** with a confirmation block:

| Element | Treatment |
|---|---|
| Question line | `enrol.withdraw.confirm.q` — "This removes you from the participant list. You can register again later." 14.5px `--ink-dim`. It states the consequence **and** the recovery. |
| `button.btn.btn--ghost` | `enrol.withdraw.confirm.yes` — "Confirm withdrawal". Border and label `--accent-lit`. The phase's only destructive treatment. Focus is moved here on reveal. |
| `.subtle-action` | `enrol.withdraw.confirm.no` — "Keep my registration". |

- `Escape` reverts to the un-confirmed state. No timeout: a confirmation that expires is a
  confirmation that vanishes while someone is reading it.
- **No animation on the reveal.** A destructive confirmation that fades in is a confirmation
  you can tap through by accident during the fade.
- interaction-states.md prefers undo over confirm, and it sanctions confirm for irreversible
  actions. Withdrawal here is **technically reversible** (D-15: re-enrolling reuses the same
  `guest_id` and clears the flag) but **not visibly so**, because the guest can never read
  their own row back. So both are shipped: the confirm step, and an explicit re-registration
  path in the state that follows.

### 9. The withdrawn state

Structurally required and easy to miss: after a confirmed withdrawal `enrolled` is `'0'`, and
a naive re-render would show a blank registration form to someone who just withdrew, which
reads as "did that work?".

| Element | Treatment |
|---|---|
| `h3.sub-h` | `enrol.withdrawn.title` — "You are unregistered" / DA "Du er frameldt". |
| `p` | `enrol.withdrawn.body` — "You are off the participant list. The numbers have been updated." |
| `button.btn.btn--ghost` | `enrol.withdrawn.again` — "Register again". Mounts the form prefilled from the retained storage. |
| `.subtle-action` | `enrol.identity.clear`, still reachable here. |

- Session only. On the next page load an unenrolled guest with a stored name gets the **form,
  prefilled**, with the normal `enrol.submit` label. That is correct and needs no new state.
- **Happy consequence, verify it:** this state contains no `#enrol-form`, so
  `enrollmentReady()` is false and the nudge bar stays down. Nudging someone to register two
  seconds after they withdrew would be the single most obnoxious thing this site could do.

### 10. The schema-not-migrated state (D-36, `PGRST202`)

The owner must re-run `supabase/schema.sql` for edit and withdraw to work. Until they do, the
RPC returns a clean `404 PGRST202`. Enrollment itself is unaffected and works throughout.

- The edit and withdraw controls **render optimistically**. They are not hidden and not
  disabled, because the site cannot know the migration state without calling.
- On `PGRST202` the tapped control's row is replaced in place by one line of `--ink-dim` body
  copy: `enrol.amend.pending` — "Changes cannot be recorded yet. Tell the host directly. Your
  registration stays as it is."
- Not a `.pending` panel, for the nested-card reason. Not the `.form-alert`, because nothing
  failed: the registration is intact and the sentence says so.

### 11. Social proof (ENR-07, ENR-08, D-19 to D-22)

`dl.facts.facts--proof`, two rows, in the fact table's own grammar.

| Label | Value |
|---|---|
| `enrol.proof.count.label` — "Expected attendance" | The total, `rows.length + sum(extra_guests)`, in `.mono` with tabular figures. A bare figure, no unit word: the label already says what it counts. |
| `enrol.proof.list.label` — "Registered" | First names, comma separated, in the normal `.facts dd` treatment. |

**Why two labels and not one sentence:** the total includes plus-ones and the name list does
not, so the two numbers visibly disagree. Rather than writing a sentence to reconcile them,
the labels are chosen so they already mean different things. "Expected attendance" honestly
includes guests-of-guests; "Registered" honestly names only people who filled the form. This
is how a real fact table would do it.

- **Alphabetical by first name, sorted client side with `localeCompare(lang)`.** The wire
  contract offers `created_at.desc`, and recent-first is precisely the social-feed reading
  D-21 rejects. Alphabetical reads as a register. It also sorts `æ ø å` correctly after `z`
  in Danish for free.
- Separator is `", "` throughout, with **no "and" before the last name**. Institutional lists
  do not use one, and localising a conjunction into a joined string across three languages is
  churn for a worse result.
- **Duplicate first names are kept.** Two guests called Maria are two people, and removing one
  would make the list disagree with the count. A class list with two Marias on it is normal.
- **Below `enrollment.showCountFrom` the entire `dl` is absent.** Not a zero, not "be the
  first to register", which reads as an empty room. D-20.
- `showAttendeeList === false` removes the second row only. The count row stays.
- **Fetch failure is silent.** The block is simply absent. Nobody standing outside a building
  needs an error message about a headcount widget. D-22.
- **No skeleton loader while fetching.** A skeleton promises content that may legitimately
  never appear, because the block is hidden below the threshold. Absence until resolved is the
  honest state.

### 12. The nudge bar (NDG-01 to NDG-08, D-27 to D-29)

The bar is built and correct (`app.js:1109-1203`). This phase makes it reachable for the first
time on any device, which surfaces four things that were unobservable until now.

#### 12a. NDG-02 as a checkable contract

"Never covers the countdown, the address, or the door video" is currently unverifiable because
`body[data-nudge="1"] { padding-bottom: 76px; }` is a guess. The bar's real height is
`12 + max(44, text) + 12 + 1px border + env(safe-area-inset-bottom)`, which is **69px on a
flat-bottomed phone and up to 103px on a notched iPhone in portrait.** The 76px reserve is
short by up to 27px on exactly the devices this site is read on.

Contract:

- JS measures `#nudge.offsetHeight` (which already includes the bar's own
  `padding-bottom: env(safe-area-inset-bottom)`) and writes it to
  `document.documentElement.style.setProperty('--nudge-h', h + 'px')`.
- Re-measure on: bar show, bar hide, `resize`, `orientationchange`, language switch (the text
  may change line count), and `window.visualViewport`'s `resize` event when available. iOS
  Safari's collapsing toolbar changes the visual viewport without firing a normal `resize`.
- `ResizeObserver` on the bar when available; guarded, degrading to the event list above.
  Same discipline phase 2 applied to `IntersectionObserver`: a missing capability degrades to
  a working fallback, never to absent.
- CSS:
  - `body[data-nudge="1"] { padding-bottom: calc(var(--nudge-h, 76px) + var(--s-2)); }`
  - `html { scroll-padding-bottom: calc(var(--nudge-h, 0px) + var(--s-4)); }` so an in-page
    jump never lands its target behind the bar.
- The static `76px` fallback stays as the value used before the first measurement and when no
  measurement is possible.

**Verifiable statement for the device pass:** with the bar shown, at 320×568, 375×667, 390×844
and 430×932, each of the countdown clock, `.addr__value` and `.video-slot` can be scrolled to
a position where no part of it is behind the bar, and the footer's last line is fully visible
at maximum scroll.

#### 12b. The toast collides with the bar

`.toast` is `bottom: var(--s-5)` (24px) at `z-index: 400`; the bar is `z-index: 100`. A toast
therefore lands **on top of** the nudge bar. Unobservable in phases 1 and 2 because the bar
has never rendered, and this phase fires toasts (registration updated, identity cleared).

Fix: `body[data-nudge="1"] .toast { bottom: calc(var(--s-5) + var(--nudge-h, 76px)); }`.

#### 12c. The bar hides while the form has focus (NEW, and it is not optional)

A `position: fixed; bottom: 0` bar with the iOS soft keyboard open sits on top of the keyboard,
jumps during the keyboard animation, or covers the field being typed into, depending on
version. It also covers the submit button of the form it is pointing at.

Contract: `focusin` anywhere inside `#enrol-form` hides the bar and releases the reserve;
`focusout` calls `renderNudge()`.

- Restoration **must** go through `renderNudge()`, never through a direct `showNudge()`, so
  `sessionDismissed` (NDG-08) and `isEnrolled()` (NDG-06) still gate it. A bar that reappears
  after being dismissed is an NDG-08 failure.
- Uses the bar's existing `data-show` transform transition, so no new motion is introduced.
- No `:has()` selector, for the Safari-version reason already stated.

### Third-party runtime surfaces touched by this phase

Neither is a component registry, but both are third-party endpoints reached from the page and
they are recorded here rather than left off the sheet.

| Surface | Origin | Mitigations |
|---|---|---|
| Supabase PostgREST | `https://aplaxdplwnnlezffatal.supabase.co/rest/v1/` | Publishable key, public by design; row level rules are the boundary. `apikey` header only. `Prefer: return=minimal` on the insert, which is what keeps the notes structurally unreadable. Unconditional `AbortController` timeout. Errors branched on `code`, never on `message`, and no `message` string is ever rendered into the page. |
| WhatsApp invite link | `https://chat.whatsapp.com/...` from `config.js` | A plain anchor. `target="_blank" rel="noopener"` on all three call sites, matching `app.js:1150`. No QR code, no `wa.me`, no `intent://`, no number to save (WA-03). Absent entirely when unconfigured. |

**The one genuinely new attack surface in this project's history:** a guest types `name`, it is
stored, and it is rendered into **every other guest's browser** through the attendee list. The
`attendees` view truncates to the first token but does **not** sanitise. The mitigation is
absolute and non-negotiable: every list item, every receipt value and every greeting is built
with `document.createElement` plus `textContent`. No `innerHTML`, no template string, no
`insertAdjacentHTML`, anywhere near `name` or `note`. This is already the house rule at
`app.js:246-249`; this is the first phase where breaking it would be exploitable rather than
merely untidy.
