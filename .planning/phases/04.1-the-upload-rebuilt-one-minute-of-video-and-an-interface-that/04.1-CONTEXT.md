## The measured diagnosis, not the impression

Taken from computed styles on the live page at 390px with `data-awake="1"` set, so these
are the values a guest actually gets, not the pre-awakening institutional ones.

| Element | border-radius | background | border | padding |
|---|---|---|---|---|
| `.uploader` | **0px** | transparent | none | none |
| `.uploader__acts .btn` | 10px | `--accent` | 1px | 0 24px |
| `.mine__remove` | 10px | transparent | 1px | 0 8px |
| `.queue` | **0px** | transparent | none | none |
| `.uploader__status` | **0px** | transparent | none | none |
| `.mine__tile` (for contrast) | **18px** | `--surface` | 1px | none |

**The finding.** This site already has a rounding system and the uploader is not in it.

`:root` ships the institutional DTU values (`--r-sm: 2px`, `--r-md: 8px`, `--r-lg: 10px`,
`--glass: 0`, `--lift: 0`) and `:root[data-awake="1"]` transitions them to `10px / 18px /
28px / 1 / 1` over roughly 1.0 to 1.4 seconds. That awakening is the page's central visual
joke: the mask is square and it softens.

The uploader declares **no radius token at all** on its own container, and its primary
button reaches for `--r-sm`, the smallest value in the system. So while the page around it
awakens to 18 and 28 pixels, the single most important control in the phase stays at 10 and
its container stays at zero with no surface underneath it. It is not a card. It is a naked
stack of a definition list, a paragraph, a button and some log lines sitting directly on
the page background.

**This is why it reads as squared, and it means the fix is not a new visual language.** It
is putting the uploader into the language the rest of the page already speaks. That matters
because the owner asked for "more modern, more rounded" and also, separately and
repeatedly, has protected the DTU parody. Joining the existing awakening satisfies both;
inventing a second rounded style would fight the first.

## Decisions taken this session

| # | Question | Decision | Consequence |
|---|---|---|---|
| D-1 | Video byte ceiling | **50 MB** | Covers one minute of 1080p on most phones. 4K is refused and must be told why, in a sentence a guest can act on. Roughly 20 videos fit the Supabase free tier. |
| D-2 | Does a video spend a photo slot | **Yes, one pool of five** | No second allowance to explain. The `photos_limit` trigger keeps counting to five regardless of kind. |
| D-3 | How many videos per guest | **At most one**, inside the five | Carries over the owner's earlier decision in `accept-one-short-video` ("one video per guest"). Five 50 MB videos from one guest is 250 MB and the free tier is 1 GB, so the ceiling has to be a rule, not a hope. Needs a `kind` column and a second count in the trigger. |
| D-4 | Maximum duration | **60 seconds**, stated explicitly and prominently | The owner asked for it in those words. It is checked client side against `loadedmetadata`, and it is written on the page above the picker rather than only in a refusal. |
| D-5 | Re-encoding | **None. Uploaded as picked.** | There is no build step and no packages in this project. `ffmpeg.wasm` is a ~30 MB dependency and `MediaRecorder` re-encoding is slow, lossy and unreliable on iOS. The byte ceiling is therefore the only size control, which is exactly why D-1 had to be a real number. |
| D-6 | Visual direction | **Soft cards, clearly modern** | Owner's pick from three. Read together with the diagnosis above: the uploader becomes a card at `--r-lg`, the feedback lines become chips, and all of it rides the existing awakening rather than hardcoding pixels. |

## What this phase must not break

Carried forward from four verified phases. A restyle that quietly breaks one of these is a
regression with no test to catch it, because this project has no test suite.

- **`photos.maxFileSizeMb` is not the video ceiling.** It is 12 and it protects the phone's
  memory before a canvas decode. Video is never decoded to a canvas, so it needs its own
  number and the two must not be reconciled into one. `config.js` already carries a comment
  making this argument about the bucket ceiling; the same argument applies again.
- **`accept="image/*"` is load bearing and documented at `app.js` around line 4925.** Adding
  `image/heic` makes Safari hand back a real HEIC that Android Chrome cannot decode. The
  video work widens this attribute and must widen it with `video/*` only, never by touching
  the image half.
- **`storagePath()` and `STORAGE_PATH_RE` are one contract read in both directions** and the
  file says so: they change together, in one commit, or every new upload becomes invisible
  with no migration available from a static page. `album.js` holds a **second copy** of that
  regex at line 139. Three places, one commit.
- **The three languages stay at parity.** 246 keys in en, it and da. Zero em dashes in
  anything a guest sees.
- **Every volatile value goes in `config.js`** and nowhere else.
- **Validation runs before the decode** (D-21, PH-07). For video the equivalent is that size
  is checked before the file is handed to a `<video>` element for metadata.
- **`prefers-reduced-motion`** is honoured by anything new that moves.
- The refusal copy must name the real reason. `photo-rejections-unexplained` is still open
  and says the current type refusal can lie when `file.type` arrives empty from a share
  sheet. Widening the validator for video is the moment to fix that, not a moment to add a
  second way to be wrong.

## Open, deliberately not decided here

- Whether a video **autoplays muted** in the album or shows a poster and a play control.
  Left to the UI spec, because it is a design answer rather than an owner preference, and
  the album page is a mosaic where six autoplaying videos would be a frame rate problem on
  the phone that page exists for.
- Poster frames. Storage has no video thumbnailing on the free tier and there is no build
  step, so a poster must either be captured client side from the first frame and uploaded as
  a second object, or not exist. Costed in the plan, not assumed here.
