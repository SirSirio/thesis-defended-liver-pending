## The finding that was not in the plan

The plan named three places the storage path shape is written:

| Where | What |
|---|---|
| `storagePath()` in `app.js` | writes it |
| `STORAGE_PATH_RE` in `app.js` | reads it back at render time |
| `STORAGE_PATH_RE` in `album.js` | a second copy, maintained by hand |

**There is a fourth**, found by reading the live schema rather than the code: a CHECK
constraint on `photos.storage_path` anchoring `\.jpg$`. It is the one that bites hardest,
because it refuses the row insert while the object upload has already succeeded. A client
widened without it produces an orphaned object in the bucket that nothing points at, and
nothing in the codebase would have explained why.

## Decisions taken while building

- **The second video is refused twice.** Client side by counting video extensions among the
  paths the device already holds, so 50 MB is not spent over party wifi discovering it.
  Server side by the trigger, which is the authority.
- **The server refusal is not routed through `hitQuota()`.** That function self-heals the
  count to five and closes the control, which is right when the register says five and wrong
  here: a guest whose only spent slot is their video would have four photographs refused that
  the register would happily take.
- **Both ceilings raise `P0001`**, so the message is the only thing separating them. This
  file's rule is to classify on `code` and never on message, and that rule is about
  PostgREST's English prose. `video_limit_reached` is our own token from our own trigger,
  matched as a substring so a future wrapper sentence does not break the branch.
- **A row lock was added to the trigger.** Two rows posted in the same instant would both see
  a count of zero and both pass. Photographs always had that race and it was survivable at
  five, because the worst case was a sixth photograph. It is not survivable at one.
- **The upload timeout is per kind**, with the arithmetic in the comment. 50 MB at a realistic
  2 Mbps is 200 seconds, so the old 60s ceiling would have aborted every large video mid
  transfer and reported it as a dropped connection, which is false and sends the guest back to
  retry the same doomed upload. Six minutes for video, unchanged for photographs.
- **The poster is the video's own first frame** via a `#t=0.1` fragment, so no second object is
  uploaded. The fallback for when no frame paints is **built, not assumed**, because iOS Safari
  is unreliable here and black is indistinguishable from a photograph of a dark room.

## An open bug closed on the way past

`photo-rejections-unexplained`, cause 1. `validateFile()` tested `indexOf('image/') !== 0` and
reported "Not an image file" for a `File` whose `type` is the empty string. iOS and Android
share sheets, the Files app and cloud providers all hand those back, so a guest picking a
perfectly good photograph was told it was the wrong kind of thing. `fileKind()` now falls back
to the name's extension when the type is absent, and only refuses when a type exists and is
neither image nor video.

Causes 2 and 3 of that todo are also addressed: the size refusal now names a number and says
what to do about it, and video is no longer refused as a category. **The todo can be closed
once the owner confirms against the actual failing files**, which is what it asks for and
which no amount of local testing substitutes for.

## Two defects caught by sending a real video through

Neither would have survived review, and neither would have been found without an actual file.

- The success line said **"One photograph is on record"** for a video. It now has three cases,
  because "1 photograph and 1 video" is a real batch and calling it "2 photographs" is the
  same lie counted differently.
- `photoKindAt()` still returned `'photo'` for everything, left over from plan 1 where it was
  a deliberate stub, so **the pip marking the spent video slot never lit**. It now reads the
  stored paths, which means it is correct without a request and stays correct on a phone that
  has not spoken to the database since.

## The honest limits

- **No video has ever reached Supabase**, so the bucket's 50 MiB ceiling, the mime type list,
  the `kind` column, the second trigger count and the `videolimit` classification are all
  **verified as code and not on the wire.** The migration has not run.
- **No real phone has been used.** The `#t=0.1` poster trick is exactly the thing that behaves
  differently on iOS Safari, and the fallback exists precisely because of that, but the
  fallback has been seen only by forcing the attribute by hand.
- **Frame rates are unknown**, as in every previous session on this project: the headless
  browser does not run animation at real speed.

## Risks the owner should hold

- **Storage is now a real cost.** 50 MB per guest against a 1 GB free tier is roughly twenty
  videos, and every view of the album page spends egress against 5 GB a month.
- **`opensAt` is still `null`.** With video accepted, an unlisted URL admits 50 MB uploads from
  anyone holding it, where yesterday it admitted 3 MiB images. This raises the severity of
  `restore-opensat-before-invitations` from high to the thing to do before anything else.
