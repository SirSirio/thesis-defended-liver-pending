# Plan 04.1-02: a video, up to one minute, through every layer

**Goal:** a guest can submit one video of up to 60 seconds and 50 MB, it spends one of their
five slots, it renders correctly in their strip and in the album, and every refusal says
something a guest can act on.

**Contract:** `04.1-UI-SPEC.md` section 6, and `04.1-CONTEXT.md` decisions D-1 to D-5.

**Depends on plan 1** because the pips, the rules strip and the chips are the surfaces this
work writes into.

---

## The ordering that matters

**The database goes first and the client goes last.** A client that can upload a video before
the bucket accepts the mime type produces a refusal from Storage that the guest reads as the
site being broken. A database that accepts video before any client sends one is inert and
harmless. So: migration, verify from the untrusted position, then client.

This is the same order phase 4 used and the same order that made the delete work provable.

---

## Tasks

### T1. The migration

New file `supabase/20-video.sql`, and the matching edits in `schema.sql` so a fresh run of the
canonical file produces the same database.

- `alter table public.photos add column if not exists kind text not null default 'photo'`
  with a check constraint allowing exactly `photo` and `video`.
- `public.album` view gains `kind`, so the renderer can tell what to build. **The view must
  not gain `guest_id`.** Section 9 of `schema.sql` exists because reading the album off the
  raw table handed out a credential.
- The `photos_limit` trigger keeps its count of five across both kinds, per D-2, and gains a
  second count: at most one row with `kind = 'video'` per `guest_id`, per D-3. Two counts, two
  distinct exception messages, because "limit reached" that cannot say which limit is a
  refusal a guest cannot act on.
- Bucket: `file_size_limit` from 3145728 to **52428800** (50 MiB), `allowed_mime_types` from
  `array['image/jpeg']` to `array['image/jpeg','video/mp4','video/quicktime']`.
- `delete_own_photo` needs no change. It keys on path and guest id and is kind blind, which is
  correct.

**The size ceiling is the real control.** The client check is a courtesy that anyone can skip
by talking to the API directly. `file_size_limit` is counted on the bytes that arrive and is
the only thing standing between this project and a storage bill.

**Verify, from the untrusted position with the publishable key, never from the dashboard:**

| Check | Expected |
|---|---|
| Insert a second `kind='video'` row for one guest | refused, with the video specific message |
| Insert a sixth row of any kind | refused, with the existing five message |
| Insert a 5th row where one is a video | accepted |
| Anon select on `public.photos` | 42501 |
| `public.album` returns `kind` and no `guest_id` | confirmed by reading the column list |
| Upload a 4 MB object | accepted, where it was refused before |
| Upload a 60 MB object | refused by the bucket, not by the client |

Plant synthetic rows for the negative tests and destroy them in the same session, exactly as
the 260818-rmv session did. **Do not touch the owner's real photographs.**

**Commit:** `feat(photos) the database accepts one video per guest inside the five`

### T2. The path contract, in three places at once

`app.js` `storagePath()` and `STORAGE_PATH_RE`, and `album.js:139`.

The extension can no longer be a hardcoded `.jpg`.

- `storagePath(ext)` takes the extension and validates it against a closed allowlist of
  `jpg`, `mp4`, `mov`. Never from `file.name`, which is guest controlled.
- `STORAGE_PATH_RE` becomes `...\.(?:jpg|mp4|mov)$`, still anchored at both ends.
- **`album.js` holds a second copy of that regex and it must change in the same commit.** The
  file's own header names this as a duplication that has to be maintained by hand. A shape
  change landing in one file and not the other makes every new upload invisible with no
  migration available from a static page.

**Verify:** an existing `.jpg` path still matches all three. A path with a traversal segment,
a query or a fragment still fails. A `.mp4` path matches. Assert the two regexes are
character identical with a one line check.

**Commit:** `feat(photos) the storage path contract admits video, in all three places`

### T3. The validator, and the refusal that stops lying

`app.js` `validateFile()`, `config.js`.

Config gains a `photos.video` block: `enabled`, `maxSeconds: 60`, `maxFileSizeMb: 50`,
`accept`. Every number in the rules strip from plan 1 reads from here.

- `validateFile()` splits: image path unchanged, video path new.
- Video: **size first, then duration.** Duration requires a `video` element and a
  `loadedmetadata` wait, so it is the expensive check and it goes second, mirroring the
  existing validate before you decode rule.
- The duration probe needs the same settle guard and timeout that `downscaleToJpeg()` has, for
  the identical reason: if neither `loadedmetadata` nor `error` ever fires, `done()` is never
  called, the queue never advances, and the pick button is disabled for the life of the page
  with no recovery short of a reload. **Reuse that shape, do not reinvent it.**
- Revoke the object URL and null the `src` on every exit, including the timeout.
- **Fix `photo-rejections-unexplained` cause 1 while here.** A `file.type` of empty string
  from a share sheet is currently reported as a wrong file type, which is a lie. Fall back to
  the extension before refusing on type. This is the moment: the type test is being rewritten
  anyway, and adding a video branch beside a known broken image branch doubles the bug.

**Verify:** a 61 second video is refused and the message names both lengths. A 60 MB video is
refused and the message says to film at lower quality. A file from the Files app with an empty
type is no longer refused as the wrong type. Record `name`, `type` and `size` for each test
file in the summary.

**Commit:** `feat(photos) video is validated on size then duration, and an empty type stops lying`

### T4. The upload path

`app.js` `runNextFile()`, `uploadObject()`.

- A video **skips `downscaleToJpeg()` entirely.** There is no canvas path for video and D-5
  refuses re encoding. It goes to `uploadObject()` as picked.
- `uploadObject()` takes a content type instead of hardcoding `image/jpeg`. That header is the
  declaration the bucket's `allowed_mime_types` is checked against, so it must be the real
  type of the bytes being sent.
- `xhr.timeout` of 60000 is wrong for 50 MB on party wifi. 50 MB at a realistic 2 Mbps is over
  three minutes. **Raise it for video specifically, do not raise it for photographs**, and put
  the arithmetic in the comment so the number is checkable.
- The row insert carries `kind`.
- `accept` on the input becomes `image/*,video/*`. The image half is untouched, per the HEIC
  trap at `app.js` around line 4925.

**Verify:** a real video uploads end to end and the row lands with `kind='video'`. The photo
path is byte for byte unchanged: upload a photograph and confirm it still arrives as
`image/jpeg` at 1600px.

**Commit:** `feat(photos) a video is uploaded as picked, and photographs are untouched`

### T5. Rendering, in the strip and in the album

`app.js` `buildMine()`, `album.js` `tileFor()` and the lightbox, `styles.css`, `album.css`.

- A video tile is a `video` element with `preload="metadata" playsinline muted` and a `#t=0.1`
  fragment on the source, so the first frame stands in for a poster with no second object
  uploaded.
- **Build the fallback, do not assume the frame paints.** iOS Safari is unreliable here. On
  `error`, or when no frame has painted by a short timer, swap to a `--surface` panel carrying
  the play glyph and the duration. A black rectangle is not an acceptable outcome.
- Duration badge, bottom right, 999px pill, mono tabular, on `rgba(11,11,12,0.72)`.
- Play glyph, centred, in a 999px disc.
- **Nothing autoplays in the mosaic.** Playback is in the lightbox, on a tap, with controls.
- The video pip from plan 1 T2 is now driven by real data.
- The lightbox gains a video branch: controls, no loop, and it must pause when the lightbox
  closes or the audio keeps playing over a closed overlay.

**Verify:** on a real phone, a video tile shows a frame or the designed fallback and never a
black box. Opening it plays with sound. Closing it stops the sound. The mosaic rhythm from
260818-rmv is unchanged: every seventh frame on a phone, every ninth on desktop.

**Commit:** `feat(photos) a video reads as a video in the strip, the album and the lightbox`

### T6. Copy, and the strip made true

`copy.js`, `config.js`.

- Every new key in en, it and da, at parity.
- Flip `config.photos.video.enabled` to `true`, which is what makes plan 1's rules strip state

- New refusal keys: too long, too large for video, second video, and the corrected empty type
  case.
- Rewrite `photos.lede`, which currently says "photographic evidence" and "five per person" and

- **Zero em dashes.** Run the sweep.

**Verify:** key count identical across the three tables, zero missing, zero em dashes, and the
site read end to end in each language with a video present.

**Commit:** `feat(photos) the copy says video, in three languages`

## Done when

- One video of up to 60 seconds and 50 MB uploads from a real phone and appears with no reload.
- A second video is refused by the database, not only by the client, and the message says why.
- A sixth file of any kind is refused by the existing five rule.
- The photograph path is provably unchanged.
- The path regex is identical in `app.js` and `album.js`.
- Three languages at parity, zero em dashes.
- The bucket ceiling is 50 MiB and was verified by a refused upload, not by reading the config.

## Risks carried

- **Storage cost is now real.** 50 MB per guest video against a 1 GB free tier is roughly 20
  videos. Worth a line in the summary and a note to the owner before invitations go out.
- **`restore-opensat-before-invitations` is still open and `opensAt` is still `null`.** With
  video accepted, an unlisted URL now admits 50 MB uploads from anyone who has it. This raises
  the severity of that todo and the summary must say so.
